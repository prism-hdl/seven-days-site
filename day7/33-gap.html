差在五处
五级顺序单发射 vs 现代高性能核

第六日的白虹把 Linux 送进了 shell。那台机器一拍只处理一条指令、严格按顺序执行；访存不返回数据，整条流水线就得等。这一集不造新硬件——只做两件事：对比第六日与第七日的白虹、讲清五处关键差异；给出三个可测量的数，作为接下来五集的验收基准。

五级顺序单发射：三处结构性限制

第六日的白虹是一台五级流水、单发射、按序执行的处理器。这个结构实现简单、行为容易验证，把 Linux 送进了 shell；但它的性能上限由结构本身决定，靠调参数无法突破。下面逐条给出代码依据与实测数据。

① 吞吐上限：每拍最多一条指令

译码段每拍只处理一条指令，五级之间各一颗边界寄存器；节拍写在 @schedule 里：

prismwhitebow/whitebow.prism · 节拍
@schedule WhitebowCpu {
    bitwidth  : { data:64 }
    pipeline  : 5 stage
    reset     : async_low
    clock     : 100 MHz, domain = single
    resource  : none
    latency   : 5 cycle
}

无论流水线里有多少条已就绪的指令，每拍最多进入一条、退休一条——IPC 的理论上限是 1.0。实测 0.787 说明流水线空闲时间已经不多，但这个上限本身无法通过调参数提高：要每拍多条，取指、译码、寄存器堆与提交口必须成组加宽（第 35 集）。

② 顺序等待：一条指令等数据，后续指令全部阻塞

冒险裁决列出十个停顿/冲刷源；其中八类停顿合成一根前端冻结信号 hold_fe——任意一类有效，PC 与 IF/ID 一并冻结：

prismwhitebow/iu/hazard.prism · 停顿与冲刷的十个源
    src_fetch = icache_miss
    src_load  = load_use
    src_div   = div_hold
    src_fdiv  = fdiv_hold
    src_dmiss = dcache_miss       // 可缓存 load 未命中 ∨ 填充中（含检出拍，见 dcache.prism 的 busy）
    src_mmiss = mmu_miss          // MMU 走表未定案：与 dcache 占用同款形状（load/store 就站在 EX/MEM 里等翻译）
    src_amo   = amo_miss          // AMO 读/写相位未走完：同款形状（读交付前/写落地前都要占住）
    src_mis   = mis_miss          // 未对齐拆两笔：第一笔只拿到半个操作数，第二笔落地前放走就是拿半字当全字
    src_br    = ex_redirect
    src_trap  = mem_except
prismwhitebow/iu/hazard.prism · 前端冻结
    hold_fe   = (src_fetch | src_load | src_div | src_fdiv | src_dmiss | src_mmiss | src_amo | src_mis) & !redirect

后果很直接：一条 load 等待 miss（几十到上百拍）、一条除法等待 35 拍，这期间后续指令即使与它完全无关，也一条都不能执行。600 拍实测中 128 拍（21.3%）空置，主要来源就是这张表。顺序语义要求"等待也按程序序排队"，这是空拍的结构性来源（第 34 集处理）。

按序的约束还体现在前递上：操作数按"在流水里的位置"分两级取——位置即年龄：

prismwhitebow/iu/hazard.prism · 两级前递
    fwd_a = match {
        (mem_reg_wen & (mem_rd != 0) & (mem_rd == ex_rs1)) => 1,
        (wb_reg_wen  & (wb_rd  != 0) & (wb_rd  == ex_rs1)) => 2,
        _                                                  => 0,
    }

这条规则的成立同样依赖"流水线严格按序"；年龄改用唯一编号（tag）之后，前递匹配方式一并更换（第 34 集）。

③ 频率上限：一拍内的组合路径过长

缓存与存储器按组合逻辑读：命中在当拍返回数据——

prismwhitebow/iu/icache.prism · 头注
// =============================================================================
// icache.prism — 指令缓存（直接映射，16 行 × 每行 4 字）
//
// 容量 64 字 = 256 字节；行大小 4 字（16 字节，装得下 4 条标准指令或 8 条 RVC）；
// 直接映射，无替换策略；命中组合读出（同拍出，与 im 的 1RW 口径一致）。

时钟周期不能短于一拍内最长的组合路径。取指这一拍里串着完整的 SRAM 读出，访存那一拍同样；切成五段之后每段仍然很长，主频因此受限。要提高频率，必须先把"读"移出当拍（改为在拍沿寄存），再细分流水段（第 36 集）。

另有两处问题被上面的结构放大

访存延迟：停顿表里 dmiss / mmiss / amo 三项都来自访存，且一次缺失就冻结整条流水线——它是空拍的最大单一来源，需要把访存改为非阻塞（第 37 集）。误预测代价：一旦流水线加深（③ 的解法），同样一次猜错要冲刷的级数更多，预测准确率的价值随之放大（第 38 集）。

对症的五种技术：各自的引入条件

上面三处限制与两处放大问题，逐一对应五种技术。每一种都有明确的引入条件与前置依赖——不是"越多越好"，而是针对哪类瓶颈、在什么前提下才成立：

要解决的问题技术引入条件前置依赖
② 顺序等待：一条等数据，后续全部阻塞乱序执行：重命名 + ROB + 发射队列 + 访存队列等待事件的时间远大于指令本身（miss 几十到上百拍、除法 35 拍），且等待点之后有足够多独立指令可执行每条指令有唯一编号（tag）；前递与唤醒从"按位置"改为"按 tag"
① 吞吐上限：IPC 逼近 1.0多发射：取指 / 译码 / 重命名 / 提交加宽单发射成为下一瓶颈：等待类停顿被处理之后，流水线中仍有可并行的指令流寄存器堆多端口、旁路网络按 tag 匹配、提交口支持一拍多条
③ 组合路径限制主频深流水 + 同步读瓶颈是频率而不是每拍条数时（组合路径无法再压缩）各级输入必须"上一拍就绪"——缓存与寄存器堆先改同步读，前端拆分流水级并加指令缓冲
访存延迟冻结整条流水线非阻塞访存 + 私有 L2 + 总线换代miss 是空拍的最大来源，且乱序已能承接"流水线继续执行"在途登记（地址表 + 填充表）；收益由乱序兑现
深流水放大误预测代价预测升级：返回地址栈 + 四件套预测器流水线加深之后，或分支密集负载上冲刷损失占比上升时无（可独立生效）；收益判据只能落在计数器上

依赖关系决定改动顺序：tag 与重命名是乱序和多发射的共同前提（多发射的旁路匹配同样靠它）；同步读是深流水的前提；非阻塞访存的收益必须由乱序兑现（没有乱序，miss 期间本来就没有指令可以继续执行）；预测升级是对深流水的回应。顺序不是任意的：先备好地基（同步读、tag），再做宽度与深度上的加法。

三个可自证的度量

判断"性能差"与"改动有效"，需要独立于实现的度量。三个量互相独立：总量（每拍退休条数）、构成（空拍按源归因）、潜力（miss 期间可退休拍数）。

度量① 每拍退休条数（IPC）

固定 600 拍窗口实测：有退休的 472 拍、空的 128 拍——IPC 0.787。单发射的理论上限是 1.0——已经离得很近。

度量② 空拍率与按源归因

128 拍空拍占 600 拍的 21.3%。关键不是这个百分比，而是每一拍空拍都能被前面十个源中的至少一个解释——归因要闭合：按"或"覆盖，不许对不上账；对不上就按拍打印十个源的取值，直接点名缺了哪一类。判据要写成"什么情况下它会红"——"覆盖率 ≥95%"那种写法永远不会红。这套账本已有硬件对应：十个源 + 两个缓存起手在 csr 里各有计数器（mhpmcounter3–14 固定绑定，事件号即位序），第 39 集把它接到跑分上。

度量③ miss 期间，还能退休几条

第三个量只有非阻塞访存的机器才有意义：从一笔 load miss 发出、到数据交付的整段里，还能退休几条指令。按序核这个量恒为 0——miss 期间整条流水线停住；只有非阻塞的机器才第一次给出非零值。它是第 37 集的核心判据。

三个量怎么用 ①②描述"当前瓶颈在哪"，③描述"改结构之后能快在哪"。每处改动前后各跑一遍同一张归因表——收益是否兑现，逐一可见。

小结

  • 三处结构性限制：每拍一条（吞吐上限）、等待连坐（顺序语义）、组合路径限制主频；另有两处被放大：访存延迟冻结流水线、深流水放大误预测代价。
  • 五种技术各有引入条件与前置依赖；改动顺序由依赖决定：先备同步读与 tag 这两块地基，再做宽度与深度上的加法。
  • 三个可自证的度量：IPC 0.787（600 拍窗口）、空拍 21.3% 且逐拍可归因、miss 期间可退休拍数（按序核恒 0）。
  • 接下来五集各处理一种技术；改动前后跑同一张归因表——先立判据，再动硬件。
