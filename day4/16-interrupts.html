中断
CLINT 与 PLIC

第 15 集那颗 CSR 留了三根线——mtip / msip / meip，当时表里全是 0——那三根线上没有接任何中断源。这一集给它们接上源：一颗管时间，一颗管排队。跑通之后才看得见：中断是两级门控，而第二级的"不点头"，才是它最容易被写错的地方。

"地要生出活物来，各从其类。" —— 《创世记》 1:24

三根线，三件事

RISC-V 把外部世界打断 CPU 的方式压成了三根线：

mtip · 机器定时器

时间到了。Linux 靠它换进程、靠它算超时——没有它，调度器就是死的。

msip · 机器软件中断

"另一个 hart 让你停一下"。多核启动、远程刷新 TLB 都靠它。

meip · 机器外部中断

设备在叫你。几十个外设共用这一根线，所以它后面必须站一个 PLIC。

还有一根内向的

第 15 集那颗 CSR 自己就能抬 mip 的位——软件写 mip 是合法的，硬件线只是最常见的那类源。

这一集两件活：CLINT 负责时间与软中断，PLIC 负责让一堆设备共用一根线。两个样例都在 examples/day4/，各自一张手算表、各自撞 RTL。

CLINT：一个一直在走的数

CLINT 里最要紧的是 mtime——一个只增不减的 64 位数，每拍 +1。第二个是阈值 mtimecmp：mtime ≥ mtimecmp 就抬 mtip。

prismexamples/day4/clint.prism · 时间与比较器
    on clock {
        r_mtime' = r_mtime + 1                       // 时间只会往前走
        if (wen & (addr == 0x4000)) { r_mtimecmp' = wdata }
        if (wen & (addr == 0x0000)) { r_msip' = wdata[0:0] }
    }

    rdata = match addr {
        0x0000 => {63{0}, r_msip},
        0x4000 => r_mtimecmp,
        0xbff8 => r_mtime,
        _      => 0,
    }

    // 两个比较器，两条线：阈值到了就一直抬着（电平，不是脉冲）——
    // 这也是为什么中断服务里必须写 mtimecmp：不挪阈值，它会一直报。
    mtip  = r_mtime >= r_mtimecmp
    stip  = r_mtime >= stimecmp
    msip  = r_msip
    mtime = r_mtime

三行代码，三个要讲清的点：

  • 复位值给全 1，不是给 0。给 0 的话上电第一拍就"时间到了"——机器还没起来就先挨一发中断。0xFFFFFFFFFFFFFFFF 在 100 MHz 下要跑一万年，等于"永远不到"。
  • 比较器是电平，不是脉冲。mtip 一旦抬起来就一直抬着，直到软件把阈值挪走。所以中断服务程序里必须写 mtimecmp——忘了这一步，中断会一直报，机器卡在"进门"上出不去。
  • Sstc 的 stimecmp 也挂在这里。它是 S 态的定时器阈值（规范里的 Sstc 扩展），比出来的 stip 走 S 态那条路。为什么放在 CLINT 里？因为它要跟 mtime 比，而 mtime 只在这一颗里。
$ prism run examples/day4/clint.prism --debug （12 拍，只摘头尾）
cycle mtip stip msip mtime 0 0 0 0 1 1 0 0 0 2 2 1 0 0 3 ← 阈值 3 到了：mtip 抬起 3 1 0 0 4 ← 还抬着（电平，不是脉冲） 4 0 0 0 5 ← 写回全 1：当拍就落 … 6 0 0 1 7 ← 软件写 msip 8 0 0 0 9 ← 写 0 才落 10 0 1 0 11 ← S 态阈值 5 到了：stip 抬起

PLIC：谁在按门铃，谁先说话

几十个设备共用 meip 一根线。PLIC 要做的就三件事：登记（谁按了）、排队（谁先说话）、销账（说完了）。

第一件事有个容易写反的细节：网关只置位、不清位。

prismexamples/day4/plic.prism · 网关与认领
    on clock {
        // ① 网关：源电平进来就置 pending，绝不在这里清
        r_pending' = r_pending | src

        // ② 配置口：priority[0..7] 占 0x0000 起的八个字；enable / threshold
        if (wen & (addr < 0x1000)) { r_prio'[addr[4:2]] = wdata[2:0] }
        if (wen & (addr == 0x2000))   { r_enable'    = wdata[7:0] }
        if (wen & (addr == 0x200000)) { r_threshold' = wdata[2:0] }

        // ③ claim：交出去 + 转 in_service（pending 清掉）
        if (hit_claim & best_v) {
            r_claimed'    = best_id
            r_pending'    = r_pending & ~(u8(1) << best_id)
            r_in_service' = r_in_service | (u8(1) << best_id)
        }
        // ④ complete：把源号还回来
        if (wen & (addr == 0x200004)) {
            r_in_service' = r_in_service & ~(u8(1) << wdata[2:0])
        }
    }

    // 通知 = 有候选，且它的优先级高于阈值。阈值只挡这一根线。
    wire best_prio : u4 = p7

为什么"只置不清"？因为源可能是很短的一个脉冲——设备按一下就松手。如果 pending 跟着源电平走，脉冲过去了中断就丢了。所以规范把它做成：源电平进来就登记，清它的唯一途径是被 claim 走。这一条让"按一下"变成"没被处理就一直报"。

第二件事是仲裁：在所有 pending & enable 里挑优先级最高的；同优先级按源号小的先来。实现上是一条从 0 号往上走的扫描链，"严格大于才顶替"——这样撞上等值时先来的那个不会被后来的挤掉。样例里 0 号（priority 1）和 2 号（priority 5）同时挂着，claim 交出来的是 2 号：

$ prism run examples/day4/plic.prism --debug （12 拍，摘关键几拍）
cycle meip claimed 4 0 0 ← 源 5 有优先级但 enable 没放行 5 1 0 ← 源 0 来：1 > 阈值 0 → 通知 6 1 0 ← 源 2 也来（优先级 5） 7 1 2 ← claim 交出 2 号，不是号小的 0 号 8 1 2 ← 0 号还挂着，通知还在 9 0 0 ← 再 claim 交出 0 号，没候选了 10 0 0 ← complete 还回 2 号（此刻无候选，不影响通知） 11 0 0 ← 阈值抬到 7：全挡

第三件事：claim 是读、complete 是写同一个地址。claim 走的源转进 in_service，complete 才把它清掉。threshold 只门控通知（meip），不门控 claim——阈值高的 context 不该被吵醒，但已经醒着的它照样能把活干完。这是规范里最容易实现错的一条。

两级门控：线抬起来，不等于要进陷阱

第 15 集那颗 CSR 收到线之后，还要过两道自己的门：mie 里对应位允许 + 全局 mstatus.MIE 打开。所以外设拼命抬线，核可以全当没看见——这不是 bug，是设计。

prismexamples/day4/intr_link.prism · 把 CLINT 接上 CSR
design IntrLinkTop {
    clint : CLINT
    csr   : CSR

    // 线：CLINT 的两根接进 CSR，PLIC 那条这一片先接地
    connect clint.mtip -> csr.mtip
    connect clint.msip -> csr.msip
    connect 0          -> csr.meip
    connect 0xFFFFFFFFFFFFFFFF -> clint.stimecmp    // Sstc 那条这一片不用

    // 这一片不动 CSR 的陷阱口，只借它的中断判定
    connect 0 -> csr.ren
    connect 0 -> clint.ren
    connect 0 -> csr.trap
    connect 0 -> csr.mret
    connect 0 -> csr.sret
    connect 0 -> csr.trap_cause
    connect 0 -> csr.trap_pc
    connect 0 -> csr.trap_val

    // 观测：一根是线，一个是 CSR 的判定
    wire mtip_v    : u1 = clint.mtip
    wire pending_v : u1 = csr.interrupt_pending
}

// 一张表说清两级门控：同一根 mtip，先不开使能，再开。
//   拍 0  给 CLINT 写阈值 3；给 CSR 写 mie = 0x80（bit7 = 定时器中断）
//   拍 1  mtime 2 < 3 → 线还低
//   拍 2  mtime 3 ≥ 3 → 线抬起；使能已开 → pending 同拍起
//   拍 3  还抬着（电平）——所以服务程序里必须挪 mtimecmp

样例同时驱动两边：给 CLINT 写阈值、给 CSR 写使能。两组地址口重名，所以 stim 里用 实例.端口 的限定写法。

$ prism run examples/day4/intr_link.prism --debug
cycle mtip_v pending_v 0 0 0 ← 写阈值 3、写 mie bit7 1 0 0 ← mtime 2 < 3 2 1 1 ← 线抬起；使能开着 → CSR 认账 3 1 1 ← 还挂着 4 1 0 ← 把使能关掉：线照样抬着，CSR 不认了

最后两拍是这一集最该记住的对照：同一个硬件、同一根线，第 4 拍与第 3 拍唯一的差别就是 mie 那一位。pending 是"线 + 使能"的与——这也是为什么调试中断时第一件事是读 mip 和 mie：先分清是"中断源没有抬线"，还是"抬了线但使能位没开"。三张表都撞了 RTL，逐拍全等。

这一片的边界

没有
真的跳进陷阱
这一片只验到"该进陷阱了"。真正跳 mtvec、保存现场、mret 回来，要等整机把流水与 CSR 接起来（第 18 集之后）。
只有
8 个中断源
白虹的 PLIC 要长到 32 源、每 context 一份 enable/threshold。教学版取 8 个，结构一样，位数不同。
简化了
mtime 的频率
这里每拍 +1；真机上一个 tick 对应 10 ns（100 MHz），固件据此换算墙上时间。
没有
优先级抢占
服务中被更高优先级打断要 context 自己管；PLIC 只保证"门铃按顺序响"。

小结

  • 三根线三件事：mtip 管时间、msip 管"叫你一下"、meip 管设备。
  • CLINT：mtime 只增、mtimecmp 复位给"永远不到"、比较器是电平（服务程序必须挪阈值）。
  • PLIC：网关只置不清、同优先级按号小、claim 交出并转 in_service、complete 才销账。
  • threshold 只门控通知，不门控 claim——醒来的人要把活干完。
  • 中断是两级门控：线抬起只是第一级，mie 与 mstatus.MIE 才决定要不要进陷阱。
