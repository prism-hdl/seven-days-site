挂根
initramfs 与它的三条软规矩

内核跑起来了，但没有根：VFS: Unable to mount root fs。把 initramfs 装进 DDR 的槽位表就能挂上，可这件事带着三条没有编译期检查的约定——地址要四处一致、启动参数得用 rdinit= 而不是 init=、镜像根上必须自带两个设备节点。三条各配一条能核对的判据。

内核起来了，但它没有根

内核起跑路上的缺陷都修掉之后（最近的一发——hold 与 trap 同拍的让位——记在第 14 集后记），内核 init 全程无 oops，终点落在一条打印上：VFS: Unable to mount root fs on unknown-block(0,0)。这不是硬件缺陷——是整机缺一份 rootfs，而且缺的方式很具体：内核找不到可以挂载的根设备，于是把 PID 1 也一起带走（panic，日志里那个进程名还是 swapper）。

选 initramfs 而不是块设备：它随镜像一起装进 DDR，内核解压它、把里面的目录树直接建成根文件系统，不需要磁盘驱动，也不需要分区表。代价是这件事有三条没有编译期检查的约定——地址要两处一致、启动参数用哪个键、镜像根上必须自带两个设备节点。这一集把三条都写成能核对的判据。

第一条：initramfs 进槽位表，长度不能凑整

第 18 集那张 DDR 槽位表在这一天多了一条。soc/soc.prism 的头注把它的形状与理由写在一起：

prismsoc/soc.prism · DDR 槽位表（内核之后那两条）
//                              +0x200000  内核      窗口 0x600000（6MB 槽位，止于 initrd）
//                              +0x800000  initrd    窗口 = 文件长度，dts 的 initrd-end
//                                               必须由同一个数算出来（tests 里有对账）

注意最后一条的窗口是"文件长度"，不是某个圆整的容量。设备树那边必须用同一个数算出 initrd-end，因为内核取的是 end - start：

dtsfw/sbi.dts · initrd 的两个地址
		/* initramfs 在 DDR 字节偏移 0x800000（基址 0x80000000 + 0x800000
		 * = 0x80800000），长度 916,480 字节 = 0xdfc00，所以 end = start + 长度
		 * = 0x808dfc00。内核按 start/end 之差取镜像长度，这个数不能凑整——少了尾巴
		 * cpio 就解不完。偏移与长度都在 soc/soc.prism 的 image 槽位表里，两处必须是
		 * 同一个数，tests/test_soc.py 拿这份 dts 与那份源码对账。 */
		linux,initrd-start = <0x80800000>;
		linux,initrd-end = <0x808dfc00>;

916,480 字节 = 0xdfc00，起点 0x80800000，终点 0x808dfc00。这个数不能凑整——把终点圆到 0x808e0000 只是多算 1024 字节不会错，但反过来少给尾巴，cpio 就解不完，症状是内核报 rootfs 解压失败，看起来像镜像坏了。真正会漂的是另一件事：这条地址事实写在四份文本里。

第二条：rdinit= 不是 init=

PID 1 起哪个程序，内核有两个键可以指，而它们在 initramfs 阶段不等价。设备树的注释记的就是这一条：

dtsfw/sbi.dts · 为什么用 rdinit=
		 * PID 1 用 rdinit= 而不是 init=：这份内核里 init= 只设 execute_command（挂上根
		 * 之后才用），initramfs 阶段看的是 ramdisk_execute_command，它默认 "/init"，而
		 * 本镜像根上没有 /init ⇒ init_eaccess 失败就直接 prepare_namespace 去挂根设备，
		 * panic 在 unknown-block(0,0)（日志里 PID 1 还是 swapper）。rdinit=/linuxrc 起的
		 * 就是这张 initramfs 根上那条指向 bin/busybox 的软链（busybox 认 linuxrc 这名字，
		 * 走 init applet 读 etc/inittab）。
dtsfw/sbi.dts · 启动参数
		bootargs = "console=ttyS0 earlycon=sbi rdinit=/linuxrc initcall_blacklist=check_unaligned_access_boot_cpu";

机制说清就是：init= 只设 execute_command，那是挂上根之后才用的；initramfs 阶段内核看的是 ramdisk_execute_command，它的默认值是 "/init"。这份镜像根上没有 /init，于是 init_eaccess 失败，内核转去 prepare_namespace 挂根设备——就是第 1 节那条 panic。两个键的名字只差三个字母，症状却隔了整个启动流程。

第三条：镜像根自带 /dev/console 与 /dev/null

PID 1 起来之后要能打印。它的标准输入输出接到 /dev/console，而这个节点在这份配置里内核不会代造：

dtsfw/sbi.dts · 镜像根上的两个设备节点
		 * 镜像根上还得有 /dev/console 与 /dev/null：这份配置 DEVTMPFS 没开，内核不代造，
		 * 缺了就是 "Warning: unable to open an initial console"，PID 1 没有 ctty。*/

这份内核没开 DEVTMPFS（开了的话内核会在挂载根之后自动造 /dev 下的节点），所以设备节点必须躺在 cpio 里。缺了它，日志上是一行 Warning: unable to open an initial console，随后 PID 1 没有控制终端——程序照跑，但没有任何输出接得到，看起来像整机挂死。镜像内容本身是可以直接列出来核对的：

terminal$ bsdtar -tf fw/initramfs.cpio
$ bsdtar -tf fw/initramfs.cpio
# 只列这一集关心的四条（根上没有 /init，所以必须靠 rdinit=）
linuxrc
bin/busybox
etc/inittab
dev/null
dev/console

第三条软规矩也在这张列表里：linuxrc 是一条指向 bin/busybox 的软链。busybox 认 linuxrc 这个名字——用它启动时走的是 init applet，读 /etc/inittab：

terminal$ bsdtar -xOf fw/initramfs.cpio etc/inittab
$ bsdtar -xOf fw/initramfs.cpio etc/inittab
# /etc/inittab

::sysinit:/bin/mount -t proc proc /proc
::sysinit:/bin/mount -t devtmpfs devtmpfs /dev
::sysinit:/bin/mount -t sysfs sysfs /sys
::sysinit:/bin/mkdir -p /dev/pts /dev/shm
::sysinit:/bin/sh

最后那行 ::sysinit:/bin/sh 就是这一日的终点：init 起来之后直接开一个 shell。它能不能真的对话，取决于串口那条路——那是第 31 集。

判据：同一件地址事实写在四份文本里，逐条核对

三条软规矩里只有第一条会漂——因为它跨四份文本，而且改一处忘另一处不会编译报错。这份核对是静态的，纯读文本，不跑仿真：

pythontests/test_soc.py · 为什么值得为地址写一份核对
def test_fw_layout_slots():
    """固件槽位表：同一件地址事实写在四份文本里，这里逐条对账（纯静态，不跑仿真）。

    动机是它真会漂：装载窗口在 soc.prism 的 image 段、传参地址在 rom.prism 的 stub
    （`lui a1/a2` 的 20 位立即数）、内核取 initrd 的地址在 fw/sbi.dts、DDR 基址在
    memmap 的 AddrWindow。改一处忘另一处不会编译报错——只会开机时读错内存。
    判据（每条都点名两处的数，任一侧动了就红）：
      1. 窗口无缝：每条的终点正好是下一条的起点，槽位之间不留缝也不重叠；
      2. stub 的 a1/a2 == DDR 基址 + 对应槽位偏移，且 info 落在 DTB 窗口之外；
      3. dts 的 initrd-start == DDR 基址 + rootfs 偏移，end-start == cpio 实际字节数
         == 那条 image 的窗口长度（省略长度时窗口就是文件长度）；
      4. 观测点跟着地址走：expose dm.ram[k] 的 k*8 == a2 - 基址；
      5. 每份镜像都存在，且装得进自己的窗口。
terminal$ python3 -m pytest tests/test_soc.py -k fw_layout -s -q
$ python3 -m pytest tests/test_soc.py -k fw_layout -s -q

其中两条与这一集直接相关：dts initrd-start == DDR 基址 + rootfs 槽位 0x800000 与 dts 的 initrd 长度 == cpio 实际 0xdfc00 B，也与那条窗口一致。第二条把三方钉在一起——设备树的两个地址、镜像文件的真实大小、以及 soc.prism 里那条装载窗口。任何一侧单独改动都会红，这是"凑整"这类手误唯一的防线。

小结

  • initramfs 是随镜像装进 DDR 的根文件系统：起点自己定（+0x800000），长度取文件真实字节数，内核按 initrd-end - initrd-start 取长度。
  • PID 1 用 rdinit=：init= 只设 execute_command，initramfs 阶段看的是 ramdisk_execute_command，默认 /init 而镜像根上没有。
  • 镜像根自带 /dev/console 与 /dev/null：这份配置没开 DEVTMPFS，内核不代造。
  • /linuxrc 是指向 bin/busybox 的软链，busybox 认这个名字并走 init applet 读 /etc/inittab。
  • 判据：地址事实的四份文本逐条核对（窗口无缝、stub 立即数、dts 两个地址 == cpio 实际字节数 == 装载窗口、观测点跟着地址走、每份镜像装得进自己的窗口）。
边界照实写

① 这份核对是静态的：它保证四份文本说的是同一个数，不保证内核真的解开了 cpio——那要看整机启动，代价是亿拍量级，收官证据放在第 31 集。② 这一集不碰块设备与文件系统镜像：initramfs 之后根仍在内存里。③ inittab 里那条 mount -t devtmpfs 在没开 DEVTMPFS 的内核上会失败——整机跑到 shell 的那份捕获里就有这一行：mount: mounting devtmpfs on /dev failed: No such device。它只是 sysinit 序列里的一条命令，不影响 PID 1 起来，也不影响提示符出现；这条留给后续清理。
