进入 shell
从"能打印"到"能对话"

串口早就在出字了，可那只是单向。要一个能输入命令的 shell，缺的是四件各自独立的事：设备树里的串口要变成 platform device、控制台要从 bootconsole 换到 ttyS0、键盘那条路要走完 PLIC 双 context 与 seip、THRE 要在中断线上。四件都不影响"能打印"，所以这一集的判据只看往返。

"能打印"与"能对话"差的是四件事

到第 31 集为止，串口已经能出字：OpenSBI 的 banner、内核的每一行打印，都从 uart8250 的 TX 落到宿主。但那只是单向。要成一个可以输入命令的 shell，缺的不是串口本身，而是四件各自独立的事：

缺的那件不做的表现在哪一层
设备树里的 serial@10000000 变成 platform device8250 驱动一次都不碰寄存器面，console=ttyS0 注册不上，用户态开 /dev/console 得 ENODEV内核配置
控制台从 bootconsole 换到 ttyS0早登期间是 SBI 代发字符，接管之后才走驱动内核与固件的交接
键盘那条路：PLIC 的双 context 与 seip 全链输出正常、输入无反应——RX 中断进不到 S 态SoC 连线 + PLIC
THRE 上中断线（第 19 集立过）用户态 write() 的前 16 字节进了 FIFO 就再无下文UART 中断源

四件事的共同点是：每一件都能让"能打印"保持不变。所以这一集的判据不看输出，看往返。

内核侧只加一行配置

随镜像入库的那份内核配置，头部就写明了它与上游的差：

textfw/prism.defconfig · 与上游的差
#   与上游那份 prism.defconfig 的差：只多点 CONFIG_SERIAL_OF_PLATFORM=y
#     （把设备树里的 serial@10000000 变成 platform device，8250 驱动才会来碰寄存器面；
#      没有它 = console=ttyS0 注册不上 = 用户态开 /dev/console 得 ENODEV），

机制是这样：设备树里那条 serial@10000000 只是"这里有个 8250"的描述，而 8250 驱动挂在 platform bus 上——它需要有人把这条 DT 节点变成 platform device。CONFIG_SERIAL_OF_PLATFORM 就是那个人。少它，寄存器面读写路径一次都不会被建立，串口却照样能被 SBI 用来打印——于是症状是"能打印、不能对话"，与硬件完全无关。绑定成功的那一刻，内核自己会讲：

terminal/tmp/shell.tx · 驱动来碰寄存器面了
$ ./run_soc.sh --out /tmp/shell --time 12000ms
10000000.serial: ttyS0 at MMIO 0x10000000 (irq = 2, base_baud = 10000000) is a 16550A

接管的那一刻在控制台上有两行：

terminal/tmp/shell.tx · 控制台换人
$ ./run_soc.sh --out /tmp/shell --time 12000ms   # 控制台换人那两行（原文，含重复打印）
printk: bootconsole [sbi0] enabled
printk: console [ttyS0] disabled
printk: console [ttyS0] enabled
printk: console [ttyS0] enabled

早登那一段是 SBI 代发的，它依赖另一条配置：earlycon=sbi 要 CONFIG_SERIAL_EARLYCON_RISCV_SBI=y 才有效，否则整条早登是空话——设备树的注释把这条也记着：

dtsfw/sbi.dts · 内核命令行的唯一来源与早登
		/* 内核 cmdline 的唯一来源就是这里（CONFIG_CMDLINE 要 EXTEND/FORCE 才参与，
		 * 我们的 prism.dts 是 CMDLINE_FALLBACK + 不 FORCE）。档位不靠 no4lvl/no5lvl 钉：核里
		 * satp.MODE 只收 Bare(0) 与 Sv39(8)，写进来的 Sv48/Sv57 整笔不落地，内核
		 * set_satp_mode() 回读探测到就自己退回 Sv39——与下面 mmu-type 一致。earlycon=sbi 要
		 * CONFIG_SERIAL_EARLYCON_RISCV_SBI=y 才有效，否则整条早登是空话。

键盘那条路：PLIC 的字节图与 seip

输入方向是中断驱动的：UART 收到字节 → 拉高 source[1] → PLIC 仲裁 → 通知线进核 → S 态 ISR 来读。这一路的地址图与规范差距都在头注里：

textsoc/ip/plic.prism · riscv,plic0 字节图
// 寄存器图（**字节偏移**，标准 riscv,plic0 的地址图；窗口由 memmap 给：字节 0xC000000
// 起 0x4000000 = 64MB，正好顶到 UART 的 0x10000000 前）：
//   0x000000 + 4×id   priority[id]（u3，0=永不转发；id 0 保留：读恒 0、写忽略）
//   0x001000          pending（u32，**只读**状态视图）
//   0x002000 + 0x80×c enable[c]（u32；c=0 → hart0 M、c=1 → hart0 S）
//   0x200000 + 0x1000×c threshold[c]（u3；转发要求 priority **严格大于** 阈值）
//   0x200000 + 0x1000×c + 4  claim/complete（读=claim：交回最高优先级的候选并登记
//                             in_service；写=complete：认写进来的 id 才放号）
//
// 每个源一位 gateway：源拉高时锁存进 pending，claim 摘走并登记"在服务中"，
// complete 才放回去——放回时源若仍是高，下一拍重新 pend。
textsoc/ip/plic.prism · 有意保留的差距（已记档）
// 与规范的差距（有意保留、已记档）：
//   · 仲裁在候选集合上取**最小编号**，不按 priority 值排序——本核与内核都把各源优先
//     级置成同一个值（Linux plic 驱动全量写 1），等优先级取低号与规范一致；优先级
//     不等时的次序留给以后（priority 寄存器本身读写如实）。
//   · 只有 2 个 context（单 hart 的 M/S）。claim/complete 的 in_service 全局一份。

两个 context 是这件事的关键：c=0 是 hart0 的 M 侧、c=1 是 S 侧，内核用的是后者。所以通知线也分两根——meip 给固件，seip 给内核：

prismsoc/ip/plic.prism · S-context 的通知
    seip = (elig1 & above1) != 0
prismwhitebow/ext/csr.prism · 核收下这一根
    in   seip       : Signal<u1>       // PLIC 外部中断（S 态；S-context 通知）

验收台里专门有一行钉 context 分家：enable1 上的源只推 seip、meip 恒 0，S 侧的 claim/complete 独立走。这一格错了，表现就是"内核收不到键盘"，而 banner 照打——所以它必须有独立判据，不能靠整机输出反推。

与第 19 集的分工：IP 与整机是两层

UART 本身（8N1 引擎、8250 寄存器面、FIFO 口径、THRE 为什么必须上中断线）是第 19 集的事。这一集用的是它的结果，两层的分界就在 host 绑定这一行上：芯片里的 UART 引脚接给宿主的文件，跑什么由镜像决定。

prismsoc/soc.prism · host 控制台绑定
// host 控制台绑定在 uart.tx_pin / uart.rx_pin：--host console=file:<前缀>。对它喂什么
// 回什么的是 `--run whitebow_soc_console` 那份回显固件（10 条，写在它的 image 段里）：
prismsoc/soc.prism · 绑定本身
        console = uart_8n1(tx = uart.tx_pin, rx = uart.rx_pin, divisor = 10)

控制台的往返能不能过，判据不看"有没有打印"，而是宿主喂进去的字节 == CPU 写出来的字节。三条下降路径跑同一份产物：

pythontests/test_soc.py · 收侧背靠背为什么是整机正控

    # 那个字节会被后来的帧覆盖（实测缺下标 16 的那个），所以这条是 RX FIFO 的整机正控。
    burst = b"ABCDEFGHIJKLMNOPQRSTUVWXYZ"
    for tag, 通路 in (("golden", "golden"), ("RTL", "rtl")):
        # 整机 golden 是固定成本 3.4s + 10.2ms/拍（约 5.2k 拍的这条≈56s），离默认
        # 60s 顶只差 4s——重机负载下会假红（实测 exit=124、收到 23/26 字节）。这条
        # 单给 180s 预算；判据仍是逐字节全等，预算不参与判定。

收官：从 banner 到提示符

整机跑一次到 shell（RTL 腿，verilator，仿真时长上限 12000 ms）。控制台输出的关键几段：

terminal$ ./run_soc.sh --out /tmp/shell --time 12000ms
$ ./run_soc.sh --out /tmp/shell --time 12000ms

这几段就是第六日的终点：Run /linuxrc as init process 说明第 30 集那条 rdinit= 生效了，console [ttyS0] enabled 与 bootconsole [sbi0] disabled 说明接管发生了，最后 BusyBox 的 ash 打出提示符 # ——/bin/sh 已经在读控制台了（这一次跑到 12000 ms 上限就停在这里）。中间那行 mount: mounting devtmpfs on /dev failed 是第 30 集边界注记里说的那件事，如实打在日志上。

要说清这份捕获没有证明什么：宿主侧的输入是在上电那一刻喂进去的，早于串口驱动建立，所以它不是一发"敲了 ls / 看到目录"的往返证据。输入侧的往返由第 4 节那两条判据钉：回显固件的逐字节相同，与 26 字节背靠背（16 深度接收 FIFO 的整机正控）。

这一集不宣称什么

① PID 1 在 U 态是内核的行为（Linux 把 init 起在最低特权级），本核的 U 态与特权门在第 20 集落地；这份控制台捕获没有插桩特权级，所以它是机制的推论，不是这一跑的观测值。② 全程无 oops / 无 panic / 无 unhandled signal 是这次跑完后的核对结论，核对方法是把 .tx 全文对这三个词扫一遍——扫描本身不是判据，常驻判据是第 30 集那套（槽位对账）与第 14 集后记的真值表。③ 交互能力只验到 shell 起提示符与输入被读到，没有验完整的登录与作业控制。

小结

  • "能打印"到"能对话"差四件事：platform device、控制台接管、PLIC 双 context 的 seip 全链、THRE 上中断线（第 19 集）。每一件都不影响输出，所以判据必须看往返。
  • 内核侧的改动只有一行 CONFIG_SERIAL_OF_PLATFORM=y——设备树描述硬件，platform bus 才让驱动来碰它。
  • PLIC 按 riscv,plic0 字节图实现，双 context 分 meip / seip；S 侧收不到键盘与 banner 照打可以同时成立，必须分开钉。
  • 控制台走 host 绑定：芯片引脚接宿主文件，跑什么由镜像决定；三条下降路径同一份产物，收侧 26 字节背靠背是 RX FIFO 的整机正控。
  • 终点：内核 init 无 oops 跑到 Run /linuxrc as init process，ttyS0 接管，BusyBox 的 ash 打出提示符。
