非对齐访存
一笔装不下，就拆两笔

一个字 8 条字节车道，地址不落在车道 0 上就有三种情形：同一个字内走车道移位，跨字不跨页拆两笔再拼接，跨页与原子交 cause 4 / 6。三档共用一张宽度表，判据只许有一份——而每一档都藏着"另一种写法在对齐激励下逐位相同"的陷阱，所以判据必须指名它靠哪几根线成立。

一笔装不下：三档判决从哪来

数据通路一个字是 64 位、8 条字节车道。地址不落在车道 0 上时，一次访问可能整个落在同一个字里，也可能横跨两个字。硬件对"未对齐"只有三种回答，而回答哪一种是地址算出来的，不是指令算出来的：

档条件硬件做什么架构结果
①未对齐，但 boff + 宽度 <= 8同一个字内做车道移位与掩码合并正常读写，不报异常
②跨字，且相邻字在同一页内拆两笔：第一笔锁字，第二拍拼接正常读写，多占一拍
③跨页，或这笔是原子（AMO / LR / SC）不拆报 cause 4（load）/ 6（store、AMO）

三档共用同一张宽度表，所以判据只能有一份。这件事的位置是被理由定下来的：

prismwhitebow/pipe/lsu.prism · 对齐判据在 LSU 产，TRAP 只编 cause
    // ---- 地址对齐判据（本子系统产，TRAP 只编 cause/委派）----
    // 为什么在这儿：同一张宽度表既是 cause 4/6 的料，也是"这笔要不要拆两笔"的料，
    // 两处各算一遍必然漂移——与缺页/访问错同一条路（LSU 产、TRAP 编号）。
    // 宽度要求按规范：LB/SB 无要求；LH/LHU/SH 看 bit0；LW/LWU/SW 看 [1:0]；LD/SD 看 [2:0]。
    // 浮点访存**并进来**（FLW/FSW 的 funct3=2、FLD/FSD=3，与普通 lw/ld 同一档）：
    // q_mem_read/q_mem_write 不覆盖 FLW/FSW，原先这里漏检，未对齐的 FLD 会安静地只读
    // 一个字的高半段，既不报 4/6 也拿不到第二个字。
    wire acc_load  : u1 = (mem_mem_read  | mem_is_fp_load)  & mem_valid
    wire acc_store : u1 = (mem_mem_write | mem_is_fp_store) & mem_valid
    wire mis_by_f3 : u1 = match mem_funct3 {
        1 => mem_alu_result[0:0],         // lh/lhu/sh：2 字节
        2 => mem_alu_result[1:0] != 0,    // lw/sw/flw：4 字节
        3 => mem_alu_result[2:0] != 0,    // ld/sd/fld/fsd：8 字节
        5 => mem_alu_result[0:0],         // lhu
        6 => mem_alu_result[1:0] != 0,    // lwu
        _ => 0,                           // lb/lbu/sb：无要求
    }

注释里那句"浮点访存并进来"记的是一个真实缺陷：q_mem_read / q_mem_write 不覆盖 FLW / FSW，所以这一处原先漏检——未对齐的 fld 既不报 4/6，也拿不到第二个字，安静地只读了一个字的高半段。这类缺陷不会崩，只会给出错的数据，所以它必须由判据抓，不能由"跑起来了"抓。

同字内：走车道，绝不拆

第一档与第二档的分界是 boff + 宽度 > 8。这一条不能省成"凡未对齐都拆"，理由写在同一处注释里：

prismwhitebow/pipe/lsu.prism · 跨字判据
    // 一笔（一个 64 位字）装不下的才算"要跨字"：boff + 宽度 > 8。dm 的字宽是 64 位，
    // 一个字 8 条字节车道，车道号 = 字节地址低 3 位；取 [2:0] 之外的位会把地址位当车道。
    // 同一个字内的未对齐访问（如 lw @2：字节 2..5）走车道移位就够——硬拉去拆两笔会让
    // sec_bytes 在 u64 上绕成负数（2+4-8），第二笔的掩码与拼接全是垃圾。
    wire acc_bytes    : u64 = match mem_funct3 {
        1 => 2, 2 => 4, 3 => 8, 5 => 2, 6 => 4, _ => 1,   // lh/lw/ld/lhu/lwu；lb/sb 无要求
    }
    wire mem_boff     : u64 = mem_alu_result[2:0]
    wire crosses_word : u1 = mem_boff + acc_bytes > 8

sec_bytes = boff + 宽度 - 8 是第二笔要写的字节数。同字内的访问套进这个式子会得到负数——而它声明成 u64，于是绕成一个巨大的无符号数，第二笔的掩码与拼接全成垃圾。这是一个只在"错误的那一档"才会出现的值，所以两档的分界必须有独立判据（见第 6 节的反证 split）。

跨字不跨页：两拍事务与它的相位

第二档要占两拍：第一拍取回低地址那个字并锁住，第二拍取回相邻字再拼接。跨拍状态只能落在一个 module 里——composer 不能自持 reg，这与第 17 集那条"A 的时序：判决与清除差一拍"是同一条理由：

prismwhitebow/pipe/lsu.prism · MisPhase 头注
// MisPhase —— 非对齐访存的相位状态（一笔只装得下一个 64 位字，跨字就要两笔）
//
// 与 AmoPhase 同一形状的理由：composer 不能自持 reg，跨拍状态只能落在一个 module 里。
// 第一笔交付那一沿锁住 word0 并把相位翻成"第二笔"；走完/被撤销清相位。
// w0 只有 load 侧用得到（store 的第二笔自带 RMW 读），锁一份不影响正确性。
prismwhitebow/pipe/lsu.prism · MisPhase 全文
module MisPhase {
    in  first_done : Signal<u1>    // 第一笔交付拍（本拍 first 就是要锁的那个字）
    in  first      : Signal<u64>   // 第一笔取回/参与合并的字
    in  clear      : Signal<u1>    // 走完 / 撤销（trap、冲刷）：相位归零
    out sec        : Signal<u1>    // 1=第二笔（高位那一半）
    out w0         : Signal<u64>   // 锁住的第一字，合并时的低位来源

    reg r_sec : u1  = 0
    reg r_w0  : u64 = 0

    sec = r_sec
    w0  = r_w0

    on clock {
        if (first_done) {
            r_sec' = 1
            r_w0'  = first
        }
        if (clear) {
            r_sec' = 0
        }
    }
}

拼接的方向不能反。反了会怎样，注释写得比任何解释都直接：

prismwhitebow/pipe/lsu.prism · 合并窗口
    // 合并窗口：第一拍就是 mem_sh；第二拍的低 n1 个字节来自**锁住的第一字**（w0），高
    // n2 个字节来自本拍取回的相邻字（word+1）——两个来源一个都不能反：写成
    // (本拍>>shamt)|(w0<<(64-shamt)) 会把相邻字摆在低位、第一字顶到高位，load 值整段错位。
    // 对齐时两式逐位相同（boff=0 ⇒ shamt=0，w0==本拍字）。
    wire mem_win : u64 = mis_ph.sec ? ((mis_ph.w0 >> mem_shamt) | (old_word << (64 - mem_shamt))) : mem_sh

最后一句是判据设计上的一个陷阱：对齐时两个方向逐位相同。所以只给对齐激励，这一根线错了也量不出来——必须有一笔真正跨字的 load（探针里的甲⑧⑨）。

跨页与原子：不拆，交 cause

第二笔的字如果在下一页，就要另一次地址翻译、另一次缺页判决——这一支不在本集范围内，直接交异常。页尾的判据是一位之差：

prismwhitebow/pipe/lsu.prism · 页尾与三根产出线
    // 相邻字在下一页：第二笔要另一次翻译、另一次缺页判决 ⇒ 这一支还不拆，交 cause。
    // 页内 512 个字 ⇒ 最后一个字的下标是 9 位的 0x1FF（不是 0xFF：那是页中间那个字，
    // 邻字还在同一页里，拒它是误拒；真页尾反而漏过去，第二笔就跨到下一页去了）。
    wire crosses_page : u1 = mem_alu_result[11:3] == 0x1FF
    wire mis_refused  : u1 = crosses_word & crosses_page
prismwhitebow/pipe/lsu.prism · 原子永不拆
    // 原子不算进这两根：AMO 是读改写，mem_read 对它恒 1，混进来会让它误报 cause 4
    wire mem_is_atomic : u1 = mem_is_lr | mem_is_sc | mem_is_amo
    // 能做的就不报：同字内走车道、跨字不跨页走两笔。这两根只产 mis_refused 那一支，
    // 与 do_split 同源——两处各判一次必然漂移（就是拆了还报 4、事务被自己的陷阱打断）。
    mem_mis_load   = acc_load  & !mem_is_atomic & mis_by_f3 & mis_refused
    mem_mis_st     = acc_store & !mem_is_atomic & mis_by_f3 & mis_refused
    // .w 要 4 字节对齐、.d 要 8 字节对齐（LR 报 load 未对齐，SC 与九种 AMO 报 store/AMO）
    mem_mis_atomic = mem_is_atomic & mem_valid & (mem_amo_word ? (mem_alu_result[1:0] != 0) : (mem_alu_result[2:0] != 0))

规范对 AMO / LR / SC 的未对齐本来就要求报异常（.w 要 4 字节对齐、.d 要 8 字节对齐），所以原子这一族不是"实现偷懒不拆"，而是拆了才不合规。cause 编号归第 15 集立起来的陷阱裁决表：

prismwhitebow/pipe/trap.prism · cause 4 与 6
        (lsu_mis_load | (lsu_mis_atomic & mem_is_lr)) => 4,
        (lsu_mis_st | lsu_mis_atomic)                    => 6,

机器与内核的边界：那颗内核没编 traps_misaligned.o

硬件合规地报了 cause 4，故事并没有结束。内核启动时有一项 warmup 会故意做一次未对齐访问来量性能，而它依赖内核自己的非对齐陷阱处理——这颗内核（S 态 + MMU）没编那个文件。设备树的注释把这条边界与撤法都记着：

dtsfw/sbi.dts · initcall_blacklist 挡的是什么
		 * initcall_blacklist 挡的是非对齐 warmup：本核对非对齐 load 报 cause 4（合规），
		 * 而这颗内核（S 态 + MMU）没编 traps_misaligned.o（arch/riscv/kernel/Makefile
		 * 只把 obj-$(CONFIG_RISCV_M_MODE) 收进去，而 RISCV_M_MODE 默认 !MMU），
		 * cpufeature.c 的 check_unaligned_access_boot_cpu 里
		 * __riscv_copy_words_unaligned 一发 `ld (page|1)` 就是 Oops/panic。
		 * 2026-10-06 撤黑名单实验实测如此（panic 栈：check_unaligned_access_boot_cpu
		 * → __riscv_copy_words_unaligned，"Oops - load address misaligned"）——
		 * 早年挂在它上面的理由（S 模式 timer 无 tick）已随 Sstc 修掉，这个显然不是。
		 * 要撤它得先让 LSU 真吃下非对齐 load（C910 那条路：LSU 拆多笔），或内核配仿真。

这不是推测：2026-10-06 撤掉黑名单实测过一次，panic 栈直接点到 check_unaligned_access_boot_cpu → __riscv_copy_words_unaligned，最后一行是 Oops - load address misaligned。两条撤法也都写在注释里——LSU 真吃下非对齐 load（拆多笔那条路），或者内核配软件仿真。这一集选了第三条：把这条 initcall 挡掉，同时把"为什么挡"留在能看见的地方。

为什么要把这条记在设备树里

黑名单看起来像一行无关紧要的启动参数，实际是机器能力与内核配置之间的一条约定。它挡住的那条 initcall 与硬件的 cause 4 是同一件事的两端——只写代码不写这里，下一次改动就会把它当残留清掉，然后在启动阶段收到一个看起来与改动无关的 panic。

判据：20 根寄存器逐条对字节模型，四发反证各红一族

三档互相会掩盖对方，所以判据必须一次覆盖三档。探针的期望值不是抄实现算的，而是另写一份字节模型：

pythontests/test_cpu.py · 三档判决为什么要一起钉
# 非对齐访存的三档判决：① 同一个 64 位字内 → 车道移位；② 跨字不跨页 → 拆两笔再拼接；
# ③ 跨页（页内第 511 个字）与原子 → 交 cause 4/6（规范允许实现对未对齐择一报异常）。
#
# 三条口径都要单独钉，因为它们互相会掩盖对方：门控写错（该拆的报了异常）时 ①② 全塌；
# 跨字判据写成"凡未对齐都拆"时 ① 会拿第二笔的垃圾；页尾判据错一位时 ③ 根本不报。
# 同源 cosim 一律无感（RTL 与 golden 读同一份表达式），所以判据必须是手算值。

探针程序本身有一段工程账要记：

pythontests/test_cpu.py · 激励不许手编
# 探针的程序由 riscv64-elf-as 汇编产出（禁手编：这一版手编踩过两次——csrrw 少了
# funct3、or 的 funct3 写成字段值 0x0E，两次都伪装成"硬件算错"，白花一轮）。
# 数据模式故意选两个不对称的字（每字节都不同）：对称模式会把"取错半字"掩盖成正确。
# handler 必须排在 260 之前——demo 的 until 是 retire_pc >= 260，放 512 的话 trap 一进
# handler 就停机，见证寄存器永远是 0（上一版就这么被自己骗过一次）。

探针的读法与写法各占一段（甲），跨页（乙）与原子（丙）各占一段，每段后面紧跟读回与陷阱见证：

pythontests/test_cpu.py · 探针激励摘录（甲⑦–⑪）

    0x00303D83,   # pc104  ld s11,3(zero) — 甲⑨ 跨字 ld（3..11）⇒ 拆两笔

    0x00003383,   # pc112  ld t2,0(zero) — 读回 word0

四发反证各打一根柱子，而且每发都规定了必须红在哪几根上——红到别处不算，红不到也不算：

pythontests/test_cpu.py · 四发反证与各自的承重位
MIS_RED = {   # 每发反证必须红在哪几根上（红到别处不算，红不到也不算）
    # 摘掉门控 ⇒ 三档全塌成"凡未对齐都报 4/6"：甲段的未对齐 load/store 一律不落地，
    # gp 见证非 0。甲⑦（lhu@6）不在这一族里——它地址是偶数，mis_by_f3 本来就 0，
    # 摘不摘门控都不该 trap；乙案也不在，它要的就是报 4。
    "gate":   {"x15", "x21", "x22", "x26", "x27", "x7", "x28"},
    # 跨字判据退成"凡未对齐都拆"：同字内那几案被拖去发第二笔，而 sec_bytes 在 u64 上
    # 绕成负数 ⇒ 第二笔的掩码是垃圾。load 侧量不出来（拼接结果里被访问的那几个字节全在
    # 64-shamt 以下，只来自锁住的第一字），**只有同字内的 store 甲⑪ 会把邻居字写花**——
    # 所以甲⑪ 与 x6 这根读回就是这一发的承重位。
    "split":  {"x6"},
    # 页尾判据差一位（0xFF 是页中间那个字）：乙案不再报 4，改成被拆两笔。承重的是
    # mcause/mtval 两根见证；rd（x11）量不出来——下一页全是 0，"半笔数据"与"不写回"
    # 落进同一个 0，这正是 rd 单独当判据的盲区。
    "page":   {"x16", "x17"},
    # 拼接方向反过来 ⇒ 跨字的两笔 load（甲⑧⑨）整段错位；同字内的和 store 都不走这根
    "stitch": {"x26", "x27"},
}

两处细节值得单独看：split 那一发在 load 侧量不出来（拼接结果里被访问的那几个字节全来自锁住的第一字），只有同字内的 store 会把邻居字写花——所以它的承重位是 x6 一根；page 那一发的 rd 也量不出来（下一页全是 0，"半笔数据"与"不写回"落进同一个 0），承重的是 mcause / mtval 两根见证。判据要指名它靠哪几根线成立，否则"通过"这两个字没有内容。

小结

  • 未对齐分三档：同字内走车道、跨字不跨页拆两笔、跨页与原子报 cause 4 / 6。三档共用一张宽度表，判据只许有一份。
  • 两笔事务的跨拍状态落在 MisPhase 这一颗 module 里（composer 不能自持 reg），与 AmoPhase 同形。
  • 拼接方向、页尾位宽、两档分界这三处，各自都有"另一种写法在对齐激励下逐位相同"的陷阱——判据必须自带跨字与跨页那两案。
  • 原子永不拆：规范对 AMO / LR / SC 的未对齐要求报异常，拆了才不合规。
  • 硬件合规不等于整机可跑：那颗内核没编 traps_misaligned.o，边界与撤法记在设备树注释里。
  • 判据：20 根寄存器逐条对独立字节模型；四发反证（门控 / 跨字 / 页尾 / 拼接方向）各红自己那一族；注入后真源码仍逐条全等。
边界照实写

① 两笔事务只覆盖"相邻字在同一页"这一种跨字情形，跨页一律报异常——这是选择，不是能力上限。② 拆两笔会让这笔访存多占一拍，代价记在 src_mis 这一根源上（第 33 集的归因表里能看到它），本集不报具体拍数收益。③ 内核侧那条 initcall 仍被挡着：本集交付的是硬件三档判决，不是内核的非对齐性能测量。
