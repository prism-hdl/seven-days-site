跑一段真程序
从 C 到裸镜像

这一集不写硬件，也不写机器码

第 9 集那份程序是手抄的：14 条指令，逐条对着手册核编码，写进 run 的内联表。十几条这个量级，手抄得起。

冒泡排序不在这个量级上。所以这一集换一条所有嵌入式开发者都走惯的路——

① 写
sort.c
一个数组、两重循环：普通的冒泡排序
② 编
riscv64-elf-gcc
-march=rv64i -mabi=lp64，地址图交给 sort.ld → sort.elf
③ 拆
objcopy
.text → sort.text.bin，.data → sort.data.bin
④ 装
image + @load
两段裸镜像分别灌进 im 与 dm 的窗口
⑤ 跑
181 拍
golden 与 RTL 逐拍全等，判据在拍 180 成立

芯片这一侧什么都没学：它只认得 im 里那些 32 位的字。把 C 变成那些字，是工具链的活——这一集就把这条通路走一遍，每一步都留真输出。

那段 C：两处故意，其余普通

csort.c · 全文
/* =============================================================================
 * sort.c —— 第二日 · 第 10 集：一段真程序（冒泡排序）
 *
 * 这颗核只认最小 RV64I，所以这段 C 有两处"故意"：
 *   1. 数组元素是 long（8 字节）——本日的访存只有双字（LD/SD），
 *      int（LW/SW）、char（LB/SB）都还不在这台机器的字典里。
 *   2. 全程没有乘除法——M 扩展是第四日以后的事。
 * 其余就是普通的冒泡排序：扫一趟，逆序就换；有一趟一个都没换就收尾。
 *
 * 程序不参与"报告"：排没排好由测试台读 dm 里那六个字判定（run 的 until）。
 * 最后那个 while(1) 只是停机——编译成一条原地自跳，CPU 留在这儿等收工。
 * ============================================================================= */

long a[6] = {9, 7, 5, 3, 2, 1};   /* 待排的六个数，初值编进镜像 */

void sort(void)
{
    long pass, j, t;

    for (pass = 0; pass < 6; pass = pass + 1) {
        long swapped = 0;
        long limit = 6 - pass - 1;
        for (j = 0; j < limit; j = j + 1) {
            if (a[j] > a[j + 1]) {
                t = a[j]; a[j] = a[j + 1]; a[j + 1] = t;
                swapped = 1;
            }
        }
        if (swapped == 0)
            break;
    }

两处故意是替这颗机器着想的：

  • 元素是 long。本日的访存只有双字：LD / SD 一条判据（funct3 == 3）。int（LW/SW）、char（LB/SB）走的宽度路，第 8 集那本字典里就没有——它们会被报成"不认识"。
  • 全程没有乘除法。M 扩展是第四日以后的事。

还有一处是替验证着想的：这段程序里没有任何"报告"。排没排好不由它说——它排完就 while (1); 停在原地，判由测试台去读 dm 里那六个字。程序自报一个完工位，判据就只是信了它一次；测试台自己读产物，判据才有自己的眼睛。

地址图：程序摆在哪儿

链接器只有一个地址空间，这颗核有两块存储、各自从 0 数自己的字节。sort.ld 就是把两边对齐的那张纸：

ldsort.ld · 全文
/* =============================================================================
 * sort.ld —— 把这段程序钉在这颗核的地址图上
 *
 * 第 9 集的 CpuTop 是哈佛结构：im 与 dm 各走各的读口，各自从 0 开始数自己的字节。
 * 但链接器只有一个地址空间，所以这里给两块存储各划一段：
 *   im  0x000..0x3FF   1KB —— 256 字 × 32 位（取指只看 pc[9:2]）
 *   dm  0x400..0x7FF   1KB —— dm 的后半；前半是第 9 集那台自测程序写 dm[0] 的地方
 * dm 一共 2KB（访存只看 ex.result[10:3]），所以 0x400 起这 1KB 是它的合法窗口，
 * 越过 0x800 就绕回 0 —— 地址图的边界是硬件给的，不是链接脚本说了算。
 *
 * .bss 不需要镜像：dm 的复位值本来就是 0（memory.prism 里 `mem ram : [SIZE] W = 0`），
 * 清零这一段交给硬件，编译器只管有初值的 .data。
 * ============================================================================= */

ENTRY(sort)

MEMORY {
    im : ORIGIN = 0x00000000, LENGTH = 1K
    dm : ORIGIN = 0x00000400, LENGTH = 1K
}

SECTIONS {
    .text   : { *(.text*) }              > im
    .rodata : { *(.rodata*) }            > im
    .data   : { *(.data*) *(.sdata*) }   > dm
    .bss    : { *(.bss*) *(.sbss*) *(COMMON) } > dm
}
$ riscv64-elf-objdump -h sort.elf; riscv64-elf-nm -n sort.elf
Idx Name Size VMA LMA File off Algn 0 .text 00000050 0000000000000000 0000000000000000 00001000 2**2 1 .data 00000030 0000000000000400 0000000000000400 00001400 2**3 0000000000000000 T sort 0000000000000400 D a

三件事要看：

  • 同一个位置有两种币种。.data 摆在 0x400：装载窗口按字节写 dm[1024:]，expose 按格写 dm.ram[128]——1024 ÷ 8 = 128，因为 dm 一个元素是 8 字节。六个数就落在第 128..133 格。
  • 有初值的进 .data，零初始化的进 .bss，而 .bss 不需要镜像。dm 的复位值本来就是 0（mem ram : [SIZE] W = 0）——清零交给硬件，编译器只管真有内容的那一段。本例只有一个带初值的数组，所以段表里连 .bss 都没有。
  • 上限是硬件给的，不是链接脚本说了算。dm 只看 ex.result[10:3]，覆盖 2KB；所以 RAM 段只能落在 0x400..0x7FF，越过 0x800 就绕回开头——那是别名，不是另一块存储。

编译、拆镜像

shbuild_sort.sh · 全文
#!/bin/sh
# =============================================================================
# build_sort.sh —— 第 10 集：C → ELF → 裸镜像
#
# 目标是一颗只认最小 RV64I 的核：-march=rv64i（不带 M / C / Zbb），
# -mabi=lp64（long 与指针都是 64 位，正好对上这台机器的双字访存）。
# 产物三个：sort.elf 用来看（段表、反汇编），两段裸镜像用来装进 cpu.prism
# 里 run 块的 image 段——芯片源码一行都不改。
# =============================================================================
set -e
cd "$(dirname "$0")"

RV=$(brew --prefix riscv64-elf-gcc)/bin
CC=$RV/riscv64-elf-gcc
[ -x "$CC" ] || { echo "缺 RISC-V 交叉工具链：brew install riscv64-elf-gcc"; exit 1; }
export PATH="$RV:$PATH"

# ① 编译 + 链接：-T 交地址图，-nostdlib 让它谁都别依赖
"$CC" -march=rv64i -mabi=lp64 -ffreestanding -nostdlib -mno-relax \
    -Os -Wall -T sort.ld sort.c -o sort.elf

# ② 拆裸镜像：.text 进 im，.data 进 dm（.bss 不用装——dm 的复位值就是 0）
riscv64-elf-objcopy -O binary --only-section=.text sort.elf sort.text.bin
riscv64-elf-objcopy -O binary --only-section=.data sort.elf sort.data.bin

wc -c sort.elf sort.text.bin sort.data.bin
$ sh build_sort.sh
6040 sort.elf 80 sort.text.bin 48 sort.data.bin 6168 total

80 字节 = 20 条指令，48 字节 = 六个数。反汇编打开是这样——这份 listing 不是我写的，是编译器给的：

$ riscv64-elf-objdump -d sort.elf
0000000000000000 <sort>: 0: 00500713 li a4,5 4: 000008b7 lui a7,0x0 8: fff00813 li a6,-1 c: 40088793 addi a5,a7,1024 # 400 <a> 10: 00000613 li a2,0 14: 00000693 li a3,0 18: 00e69a63 bne a3,a4,2c <sort+0x2c> 1c: 00060663 beqz a2,28 <sort+0x28> 20: fff70713 addi a4,a4,-1 24: ff0714e3 bne a4,a6,c <sort+0xc> 28: 0000006f j 28 <sort+0x28> 2c: 0007b583 ld a1,0(a5) 30: 0087b503 ld a0,8(a5) 34: 00168693 addi a3,a3,1 38: 00b55863 bge a0,a1,48 <sort+0x48> 3c: 00a7b023 sd a0,0(a5) 40: 00b7b423 sd a1,8(a5) 44: 00100613 li a2,1 48: 00878793 addi a5,a5,8 4c: fcdff06f j 18 <sort+0x18>

两处值得停。内层循环体被摆在函数末尾（0x2c..0x4c），判头在 0x18，两头靠 bne / j 来回——所以 pc 不会从 0 一路递增。另一处是 0x28 那条 j 28：它就是 while (1);，一条原地自跳，与第 9 集手抄程序末尾那条 jal x0, 0 同一个形态。至于 li / beqz 这些助记符，落进二进制的是真指令（addi / beq）。

这颗核认不认得这份产物，判据只有一条：每条编码落在第 8 集那本字典里。把 20 条按 (opcode, funct3) 归一次类——

opcode · funct3条数是什么走 Decoder 哪条路
0x13 · 09addi（含 li）I-ALU，alu_src=1
0x03 · 32ldload，mem_ren=1
0x23 · 32sdstore，mem_wen=1
0x37 · 01luiu_sext : i32 那条位形
0x63 · 0/1/51/2/1beq · bne · bge分支借 ALU（顶层那张 alu_op_b）
0x6f · 0/71/1jal（j 28 与 j 18）is_jal：一条停机自跳、一条回循环头

9 种组合、20 条，没有一条需要给硬件加线。第码对不对由编译器负责；我只核对一件事——这颗核认不认得它。

镜像写在测试台上

装阵列的手续在第一日第 2 集就讲完了：一个别名、一块存储、一个字节偏移、一个长度。到这里它第一次拿来装别人产出的东西——而且两个窗口：代码进 im，数据进 dm。

prismcpu.prism · bubble_sort
// bubble_sort —— 第十集加的第二个 run：还是这颗 CpuTop，一行都不改，只换镜像。
// 这一回的镜像不是手抄的第码，是 riscv64-elf-gcc 从 sort.c 打出来的 ELF 拆出来的
// 两段裸二进制（build_sort.sh）：.text 进 im，.data 进 dm。
// 窗口两个数都是字节：dm 的偏移 1024 = 链接脚本里 .data 的 VMA 0x400，
// 长度由文件自己量（48 字节 = 六个字）。.bss 那个完工位不用装——dm 的复位值就是 0。
// 判据不问程序"你排完了吗"——它自己读 dm 里那六个字：数组没升序，它就不成立。
// ----------------------------------------------------------------------------
run bubble_sort of CpuTop {
    image : {
        prog : im[0:]    = @load("sort.text.bin"),   // .text：20 条指令，80 字节
        data : dm[1024:] = @load("sort.data.bin"),   // .data：9,7,5,3,2,1 → dm[128..133]
    }
    until : (a0 == 1) & (a1 == 2) & (a2 == 3) & (a3 == 5) & (a4 == 7) & (a5 == 9)
    show  : { pcv, a0, a1, a2, a3, a4, a5 }
}

两句口径要记：

  • 窗口两个数都是字节，零点是这块 mem 的起点。im[0:] 的字节数省掉了——由 sort.text.bin 的长度量出来（80 B = 20 条）；dm[1024:] 那个 1024 就是链接地址 0x400。
  • 别名是命令行的把手。--image prog=<文件> 只换文件，落点与窗口仍是源码里的事实——这一点下面反证那节要真用它一次。

181 拍

▸ prism run examples/day2/cpu.prism --run bubble_sort --debug（节选）
[run] bubble_sort: 181 拍 golden 直跑完成 # run: bubble_sort design: CpuTop stop: until true at cycle 180 cycle pcv a0 a1 a2 a3 a4 a5 0 4 9 7 5 3 2 1 # 拍 0 看见的就是灌进去的六个数 5 24 9 7 5 3 2 1 6 44 9 7 5 3 2 1 # 跳进函数末尾的内层体 10 60 9 7 5 3 2 1 11 64 7 7 5 3 2 1 # 第一条 sd 落地：低格变 7 12 68 7 9 5 3 2 1 # 第二条 sd：高格变 9 …（13 – 176 略：一趟一趟扫，最后一次换位在前头） 178 60 2 1 3 5 7 9 179 64 1 1 3 5 7 9 180 68 1 2 3 5 7 9 # 六个数成形，until 当拍成立 # stop: until true at cycle 180

三处值得停：

  • 一次换位改两格，分两拍看见。拍 11 低格从 9 变 7、拍 12 高格才从 7 变 9；中间那一拍数组是 7 7 5 …。两个 sd 之间本来就有这个半完成态——它不是 bug，是这两条指令要各落一个边沿。
  • pc 的轨迹跟着编译器的摆法走：4→8→…→24→44→…→68，再一条 j 回 24。想按手写程序的直觉去核对拍数会一头雾水；能核对的是格子值。
  • 判据成立的那一拍，就是数组最后一次变化的那一拍。拍 180 之前它一直是假，拍 180 六个字同时对上——因为判据读的就是这六个字本身，中间没有任何"程序宣布完成"的环节要等。
▸ 两条腿撞一次
$ prism cosim examples/day2/cpu.prism --run bubble_sort [run] bubble_sort: RTL tb 跑完，181 拍（产物 …） [run --cosim] ✅ PASS: bubble_sort golden == RTL 仿真（181 拍 × 7 列全等； golden stop: until true at cycle 180）

一条腿要交代清楚：这个 run 的 until 引用了 expose 出来的阵列格，TLM 后端在这条路上还生成不出合法代码（error: no member named 'read' in 'V4'）。所以这一段撞的是 golden 与 RTL 两条腿，SystemC 那条等后端补上再撞。

这条判据会不会骗你

判据读的是产物，那它有没有牙？两发实测，芯片、地址图、装载语句一个字都不动。

① 只把排序的比较写反——if (a[j] > a[j+1]) 改成 <，重跑 build_sort.sh。数组从初值起就没动过（降序对它来说"已经有序"），pc 停在自跳那一格：

▸ ① 判据行 + 尾部（加 --time 2us 有界看一眼）
[run] ❌ [run bubble_sort] until 判据在 10000 拍内从不成立——停机不可达 cycle pcv a0 a1 a2 a3 a4 a5 197 40 9 7 5 3 2 1 198 40 9 7 5 3 2 1 199 40 9 7 5 3 2 1 # 六个字一直没对上，判据就一直不成立

② 把判据换成拍数——镜像还是①那份坏掉的，只把 until 写成 for 200 cycles：

▸ ② 同一份坏镜像，判据只数拍子
$ prism run examples/day2/cpu.prism --run bubble_sort \ --image prog=/tmp/inj_a/sort.text.bin --debug # run: bubble_sort design: CpuTop stop: for 200 cycles cycle pcv a0 a1 a2 a3 a4 a5 198 40 9 7 5 3 2 1 199 40 9 7 5 3 2 1 # 退出码 0，"跑完了"——可数组就是初值

①与②是同一份机器码、同一份数据，差别只在判据读什么。读拍子，它永远绿；读那六个字，它就只有一种绿法——数组真的排好了。

这一发还顺手演示了别名怎么用作把手：--image prog=<文件> 换掉的只有文件，im[0:] 那个落点仍是源码里的事实。

小结

  • 程序来自 C → ELF → 裸镜像：20 条指令、六个数据字，一条都不用手抄；地址图由 sort.ld 说清，字节与格的换算写在窗口里。
  • 芯片一行没改，image 的两个窗口把镜像分别灌进 im 与 dm；--image 换的只是文件。
  • 181 拍把 9 7 5 3 2 1 排成 1 2 3 5 7 9，golden 与 RTL 逐拍逐列全等。
  • 判据不读程序的自报，只读 dm 里那六个字——所以程序坏掉它就永不成立，而把它换成数拍子，同一份坏镜像立刻"通过"。

第二日到这一集收束：从一颗 pc 到一段别人编译出来的程序。这台机器接下来要学的不是更多电路，是更快的节拍与会疼。
