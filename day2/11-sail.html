第四方对撞
官方 sail 模型

前面十集里，"对撞全等"反复出现。可 golden、RTL、TLM 是同一棵 AST 下降出来的——前端共有的 bug，三家会一起错。这一集请第四方进场：RISC-V 官方规范的可执行模型，不共享我们任何一行前端代码。

"有晚上，有早晨，是第二日。" —— 《创世记》 1:8
← 第 10 集 · 跑一段真程序 第三日 · 立 flag：缺的四样 →

三条腿站得稳，不等于站对了地方

第 9 集让 CpuTop 三腿全等，第 10 集让冒泡排序在 golden 与 RTL 上逐拍对上。这些对撞证明了一件事：同一份 Prism 源码下降出的三台执行者，行为一致。

但它证明不了另一件事：这份源码本身，与 RISC-V 规范一致。三条路径都由同一棵 AST 下降——译码器把 sraiw 认成别的、把 W 型结果漏掉符号扩展、把分支偏移算错一个字节，这类前端错误会被三台执行者忠实地一起执行。对撞照样全绿，程序照样跑完——只是算错了。

上一集的判据差一点就漏在这上面。冒泡排序的判据是"dm 里那六个字升序"，它能证明排序逻辑对；可那条 bge（顶层借 SLT 做的比较）如果被译码成别的形态，六个字同样会升序——判据没覆盖到的地方，三条通路一起失效。

为什么是 sail

要查出这种错，得找一个不共享前端的第四方参考。它必须满足三条：

要求为什么要sail 的答案
独立实现跟我们的前端无血缘，才能照出前端的错riscv-sail 是 RISC-V 官方的规范可执行模型，按 ISA 手册写，不按任何一家 RTL 写
权威错的判据不如没有判据——它说对才算对官方仓库、被 ISA 规范引用；分歧发生时默认先怀疑我们
能用机器喂要能逐条比，不能靠人眼看波形它输出退休序：每条指令的 pc、目的寄存器、写回值

所以这一集请进来的不是"另一个仿真器"，而是第四个裁判：golden / RTL / TLM 三条通路互相印证，sail 站在它们之外，只与退休序逐条比对。

它不是来替 cosim 的

sail 比的是退休序的 pc / rd / 写回值——访存与 CSR 行这一版不取，时钟精确性它也不管。它管的是"这条指令在这台机器上该不该这么算"。所以用法是加一条腿，不是换一条腿。

怎么请进来

不用自己编译 Sail。deps 一次装齐，版本钉死：

bash装上第四方
prism deps             # 自检：iverilog / C++ / SystemC / sail_riscv_sim 各在不在
prism deps --install   # 缺什么装什么（sail 钉 0.14.1，落 ~/.local/share/prism/tools/）

prism deps | grep sail
  [ok] sail_riscv_sim：0.14.1

找不到时按 PRISM_SAIL 环境变量 → PATH 的顺序找；两者都没有，--sail 会直接拒绝跑（不会静默跳过对撞）。

使用要点

四件事说清：喂什么镜像、看哪几列、比什么、失败长什么样。

① 两种喂法

--sail <文件> 喂一段小端整字镜像；或者 --sail-mem <实例>.<mem> —— 直接取设计里那块 mem 的初值，不复制程序。第二日这颗核的程序是 run 的 image 段灌进去的，用后者最省事：

bash两种喂法
prism run cpu.prism --run sail_check --sail prog.bin     # 给一段裸镜像
prism run cpu.prism --run sail_check --sail-mem im.ram   # 取设计里 im 这块 mem 的初值

② 看哪几列：五根约定名

对撞按列名约定取退休序：retire_valid / retire_pc / retire_rd / retire_wen / retire_data。第二日这颗核是单周期、没有"退休"这个概念，所以要把这五根从已有信号上导出来——不是加硬件，只是给已有的线起约定名：

prismexamples/day2/cpu.prism · 退休序对齐
    obs : RetireObs
    connect 1           -> obs.d_valid
    connect pc.addr     -> obs.d_pc
    connect ctl.reg_wen -> obs.d_wen
    connect ctl.rd      -> obs.d_rd
    connect wb_data     -> obs.d_data
    wire retire_valid : u1  = obs.q_valid
    wire retire_pc    : u64 = obs.q_pc
    wire retire_wen   : u1  = obs.q_wen
    wire retire_rd    : u5  = obs.q_rd
    wire retire_data  : i64 = obs.q_data
}

这里有一处易错点值得单独说：逐拍表读的是拍末的值，而 pc 在拍末已经是下一条的地址。直接把 pc.addr 报出去，对撞会从头差一拍——idx0: pc prism=0x4 / sail=0x0。所以五个字段一起过一颗一拍延迟的观测寄存器（RetireObs），行号才与 sail 的退休序对齐。

③ 比什么

逐条比 pc、rd 与写回值。缺列时它拒绝降级——不会退化成"只比 pc"给你一个好看的结果：

$ prism run examples/day2/cpu.prism --run cpu_check --sail-mem im.ram
[run --sail] ❌ 观测缺列 ['retire_valid', 'retire_pc']（--sail 按列名约定取退休序： retire_valid/retire_pc/retire_rd/retire_wen/retire_data）；本 run 现有列： ['dm0', 'pcv', 'x1', 'x11', 'x12', 'x13', 'x2', 'x8']

这是设计上的选择：宁可不跑，不给假绿。配上 --sail-base / --sail-entry / --sail-size / --sail-xlen / --sail-config / --sail-sim，以及可重复的 --sail-set 键=JSON值（只认 sail 默认配置里已存在的键，拼错当场报错）。

反证：让三条通路一起失效

上面说过——同源的错，三条腿查不出来。那就真做一个：把 W 型的后处理摘掉（slliw / sraiw 的结果不再按 32 位域解释），其余一行不改。

$ prism cosim .inj_w.prism --run sail_check （注入版：golden vs RTL 自比）
[run --cosim] ✅ PASS: sail_check golden == RTL 仿真（40 拍 × 5 列全等）

自家三条腿——全等。因为错在前端，三台执行者一致地执行这个错。再看第四方：

$ prism run .inj_w.prism --run sail_check --sail-mem im.ram --sail-xlen 64
[run] sail_check: 40 拍 golden 直跑完成 [run --sail] ❌ FAIL: 1 处分歧（prism 40 条 / sail 40 条；pc/rd/wdata）： idx21 pc=0x24: prism x12<-0x80000000 / sail x12<-0xffffffff80000000

一条就抓到。0x24 是 slliw x12, x9, 31——规范说 32 位域算完要符号扩展回 64 位（0xffffffff80000000），注入版给了 0x80000000。这就是第四方的全部价值：它不跟我们共享任何一个前端字节。

判据要跑到能看见分歧的那一拍

上面这条 idx21 在 20 拍窗口里是抓不到的——程序先跑五圈循环，第 21 条退休才轮到 slliw。窗口开小了，注入版照样"全等"。反证必须覆盖到它想证的那条指令。

代价与边界

它不管
时序与访存副作用
退休序里没有访存写、没有 CSR 行——那些仍归 cosim 与专门的探针管。
它要求
五根约定列
单周期核要自己导退休序（一颗一拍延迟的观测寄存器）；流水核则由提交级天然提供（一根 commit 脉冲就是干这个的）。
它换来的
一个外部的第四方参考
从这一集起，"对撞全等"才有资格升级成"与规范一致"；后面造真核的每一集，sail 都会跟着跑。

小结

  • 三条腿（golden / RTL / TLM）同源：它们互证的是"下降一致"，不是"符合规范"。
  • 第四方 = RISC-V 官方 sail 模型：独立实现、官方权威、能吐退休序。
  • 用法三件：--sail-mem 实例.mem 喂设计里的镜像；五根 retire_* 约定列；逐条比 pc / rd / 写回值，缺列拒跑。
  • 对齐是硬要求：逐拍表读拍末值，pc 已指向下一条——五根一起延迟一拍才对齐。
  • 反证实测：摘掉 W 后处理，golden 与 RTL 自比全等，sail 一条抓到 idx21。
