    理解世界
    decoder

    前三颗器官：会走、会记、会算。但它们不知道该做什么——指令流进来只是一串 32 位的 0 和 1。这一集造最后一颗器官，它唯一的本事是理解。

    "将水分为上下。" —— 《创世记》 1:6
    ← 第 7 集 · ALU 第 9 集 · 观察它们的心跳 →

    四颗里最"干净"的一颗

    decoder 是四颗器官里唯一完全不碰数据通路的：它不参与运算、不保存状态，输出只是一束控制位与几个地址。整颗模块由纯组合表达式与 match 构成——没有 reg、没有 mem、没有 fsm。

    输入
    instr
    一条 32 位的指令字
    输出 · 地址
    rd / rs1 / rs2 / imm
    送给寄存器堆、ALU、PC
    输出 · 许可
    reg_wen / mem_ren / mem_wen / is_branch…
    决定这一拍允许什么发生

    这个形状就是第一日讲的"理解 = 把外界字符串翻译成内部动作"。decoder 从不做事，只发号施令——做不做是别人的事。

    第一步：把 32 位切开

    RISC-V 的指令字是一套固定格式的位域拼图。理解的第一步就是切片：

    prismdecoder.prism · 字段抽取（节选）
        // ---- 字段抽取 ----
    opcode = instr[6:0]
    funct3 = instr[14:12]
    funct7 = instr[31:25]

    rd_raw = instr[11:7]
    rs1    = instr[19:15]
    rs2    = instr[24:20]

    [hi:lo] 是位切片。注意 opcode / funct3 / funct7 都在所有指令格式里位置相同——这是 ISA 设计时刻意留的：解码器可以先看 opcode 判大类、再看 funct3/funct7 判细分，而不必先知道整条指令长什么样。

    第二步：立即数的五种拼法

    立即数（指令里内嵌的常量）是最麻烦的部分——五种指令格式，五种把位数重新排列的方式。RISC-V 这么做是为了让所有格式里"该固定的字段固定"：

    prismdecoder.prism · 立即数（节选）
        // I-type：取高 12 位，再手工符号扩展
    i_raw = instr >> 20
    i_imm = i_raw >= 0x800 ? i_raw - 0x1000 : i_raw

    // S-type：高 7 位 << 5，接低 5 位；再手工符号扩展
    s_raw  = (((instr >> 25) & 0x7f) << 5) | ((instr >> 7) & 0x1f)
    s_imm  = s_raw >= 0x800 ? s_raw - 0x1000 : s_raw

    // B-type：imm[12|11|10:5|4:1|0] —— 位被拆成四段重新拼
    b12    = (instr >> 31) & 0x1
    b11    = (instr >> 7)  & 0x1
    b10_5  = (instr >> 25) & 0x3f
    b4_1   = (instr >> 8)  & 0xf
    b_raw  = (b12 << 12) | (b11 << 11) | (b10_5 << 5) | (b4_1 << 1)
    b_imm  = b_raw >= 0x1000 ? b_raw - 0x2000 : b_raw
    这一版我写错过一次——而且测试没喊

    第一版 i_imm 我只写了一行：i_imm = instr >> 20。看起来和第 7 集 ALU 的逻辑右移一样干净。向量跑完 9/9 全等 ✅。

    然后我加了一条 addi x11, x0, -8（编码 0xff800593）——立刻红：期望 -8，实得 4088。

    原因：instr 是无符号的 Signal<u32>，>> 是逻辑右移，不会替我们补符号位。之前 9 条向量的立即数全是正数——正数的符号扩展和零扩展结果一样，所以测试全绿，但代码是错的。

    修法是显式判"够不够半个范围再减回去"，S / B / J 三型本来就这么写的——只有 I 型因为"看起来能偷懒"而漏了。这就是那条老规矩：一个测试从没失败过，说明它还没被测到。

    第三步：分派

    prismdecoder.prism · 分派（节选）
        // R 型与 I 型共用同一张 funct3 表；funct7 == 0x20 是"算术变体"标志
    alu_op_r = match funct3 {
        0 => (funct7 == 0x20) ? 1 : 0,   // SUB / ADD
        1 => 5,                          // SLL
        2 => 7,                          // SLT
        3 => 9,                          // SLTU
        4 => 4,                          // XOR
        5 => (funct7 == 0x20) ? 6 : 8,   // SRA / SRL
        6 => 3,                          // OR
        _ => 2,                          // AND
    }

    // ---- opcode 分派：一次判完"这是什么指令" ----
    is_r      = (opcode == 0x33)
    is_i_alu  = (opcode == 0x13)
    is_load   = (opcode == 0x03)
    is_store  = (opcode == 0x23)
    is_lui    = (opcode == 0x37)
    is_auipc  = (opcode == 0x17)
    is_b      = (opcode == 0x63)
    is_j      = (opcode == 0x6f)
    is_jr     = (opcode == 0x67)

    reg_wen   = is_r | is_i_alu | is_load | is_lui | is_auipc | is_j | is_jr
    mem_ren   = is_load
    mem_wen   = is_store
    is_branch = is_b
    is_jal    = is_j
    is_jalr   = is_jr

    到这里，"理解"就写完了。每条控制位都是几条布尔式的与或拼接——没有循环、没有状态、没有时序。

    一个不易察觉的坑：store 的 instr[11:7] 不是 rd

    S 型格式把低 5 位当 imm[4:0] 用——那一格根本不是目的寄存器。如果 decoder 不门控就把 rd_raw 报出去，store 指令会顺手把一个随机值当寄存器号送到寄存器堆。所以最后加一行：

    rd = reg_wen ? rd_raw : 0

    不写回时把目的寄存器报成 0——等于写 x0，天然无害。防御性默认值比"下游自己小心"可靠。

    跑起来：九条指令，九次"理解"

    逐条看几处关键：

    • 拍 2（sub）：funct3=0 和 add 一样，靠 funct7 == 0x20 才分出 alu_op=1。同一格 opcode 里的两条指令，靠另一个字段区分。
    • 拍 4（sw）：mem_wen=1、reg_wen=0、imm=8——它是 store，不写寄存器，但立即数照样解析出来（地址偏移）。
    • 拍 6（beq）：is_branch=1、reg_wen=0、imm=16——分支不带写回，但它的立即数是跳转偏移，等四颗合体时它会接到 PC 的 target。
    • 拍 8：imm = -8——负立即数。这一行是后补的，也正是它逮出了上面那个 bug。
    • 拍 9：opcode=0x7f 不认识 → is_illegal=1。理解不了就说"我不懂"，而不是猜一个动作出来。
    is_illegal 只是一个位，谁来用它？

    decoder 只负责"举手报告"，怎么处置是 CPU 顶层的事：合体成 cpu_top 时会把 is_illegal 当门，把写使能全掐掉。白虹单周期核里的写法是 wire rf_wen_eff : i1 = dec.reg_write_eff & legal -> rf.wen——一条线把"非法"翻译成"这一拍什么都不许落地"。第五日还会再加一层：非法指令同时触发异常，跳到 mtvec。

    小结

    四颗器官造齐了。回头看它们各自把"水"分在了哪里：

    pc
    控制 → 数据
    入：load / target；出：addr
    regfile
    地址 / 使能 vs 值
    raddr / waddr / wen 是控制，rdata / wdata 是数据
    alu
    op vs a / b
    选路信号从不参与运算
    decoder
    整颗都是控制
    数据只在 instr 里路过
    "将水分为上下。" —— 《创世记》 1:6

    下一集是第二日最后一集——观察它们的心跳。四颗器官此刻都各自活着，我们要做的最后一件事是：证明它们真的活着，而且证明"如果它们坏了，测试会喊"。

    练习

    1. 给 decoder 加一条 jalr（opcode 0x67）的检查——它已经在 is_jr 里了。跑一条 jalr x0, 0(x1)（编码 0x00008067），看 rd 是否报 0、is_jalr 是否为 1。
    2. 把 rd = reg_wen ? rd_raw : 0 的 0 改成 rd_raw（即不门控），跑一次——sw 那一拍的 rd 变成了什么？这个值送到寄存器堆会有什么后果？（提示：wen=0 所以不会真写，但如果将来有人接了别的通路呢？）
    3. 把 known 的成员列表删掉 0x63（分支）——beq 也会被判非法。想想：真实的 CPU 里"不认识某条指令"和"这条指令不该在此时出现"，是同一件事吗？
