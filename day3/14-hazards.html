七日创造 · 第三日 · 天上光体 · 第 14 集

冒险
停顿 · 前递 · 冲刷

第 13 集把流水线摆好，四组段寄存器的 hold / kill 全接了 0，程序得自己留距离。这一集把那些 0 换成一根根真信号——全核只有一个地方有资格说"停"和"冲"。

"神说，天下要聚在一处。" —— 《创世记》 1:9

流水线的代价，在这一集暴露

第 13 集那份程序里有一排 nop，它们不是装饰：段寄存器把指令隔开，也就把它们的读写时刻错开了。add x3,x1,x2 紧跟在两条 addi 后面，就会读到还没写回的旧值——那一发注入把 x3 钉在 0 上。

错开有三类，解法各不同：

写在前，读在后
前递
结果其实已经算出来了，只是还没进寄存器堆——那就别绕寄存器堆，直接递到 ALU 门口。
递不了的
停顿
load 的数要等这一拍走完才落进下一颗段寄存器。递不了就让后面那条原地等一拍。
读在前，写在后
冲刷
分支要到 EX 才知道跳不跳，可取指早已跑到前面两条去了——那两条作废。

三类裁决全部收在一颗纯组合模块里：module Hazard。别的模块只负责执行它的结论。

一个裁决者

Hazard 没有一拍状态——它看的三件事都住在别的段寄存器里，它只负责把它们对齐比较。判据一共六行：

prismexamples/day3/pipe5h.prism · Hazard 的判据
    // 递不递：编号对得上、而且那条真的要写寄存器堆。x0 那道门在 RegisterFile 里，
    // 这里再挡一次是省 mux——rd==0 的写根本不该成为前递源。
    // EX/MEM 不递 load 的数：那颗数要等 MEM 这一拍走完才落进 MEM/WB。
    // 第二日用的 RAM 是组合读、这一拍就摆在那儿，可真实 SRAM / cache 不是——
    // 按"递不到"设计，于是 load-use 必须停一拍。
    wire m_writes : u1 = mem_valid & mem_reg_wen & !mem_is_load & (mem_rd != 0)
    wire w_writes : u1 = wb_valid  & wb_reg_wen  & (wb_rd  != 0)
    wire from_mem_a : u1 = m_writes & (mem_rd == ex_rs1)
    wire from_mem_b : u1 = m_writes & (mem_rd == ex_rs2)
    wire from_wb_a  : u1 = w_writes & (wb_rd  == ex_rs1)
    wire from_wb_b  : u1 = w_writes & (wb_rd  == ex_rs2)

    // EX/MEM 压 MEM/WB：离 EX 越近的源越新，优先级不能反
    fwd_a = from_mem_a ? 1 : (from_wb_a ? 2 : 0)
    fwd_b = from_mem_b ? 1 : (from_wb_b ? 2 : 0)

    // load-use：正在 EX 的这条是 load，它的数要等这一拍走完才进 MEM/WB，
    // 而正在 ID 的那条下一拍就要拿它当源——递不了，只能让 ID 原地停一拍。
    wire id_wants_it : u1 = (ex_rd == id_rs1) | (ex_rd == id_rs2)
    load_use = ex_valid & ex_is_load & (ex_rd != 0) & id_wants_it

    redirect  = ex_valid & ex_branch_taken
    hold_ifid = load_use
    kill_idex = load_use | redirect

三处值得停一下：

  • 编号要带下来。判等拿的是 ex_rs1 / ex_rs2，而第 13 集的 IdEx 只带了值。所以那颗段寄存器这一集多长了几根：d_rs1、d_rs2、d_funct3、d_is_branch。段寄存器的字段会增多，就是因为下一段要知道"这条是谁"，不能只知道"这条拿到什么"。
  • 优先级不能反。fwd_a = from_mem_a ? 1 : (from_wb_a ? 2 : 0)——离 EX 越近的源越新。反过来的话，一条更早的写会盖掉刚算出来的结果。
  • rd == 0 不当前递源。x0 那道门在寄存器堆里，这里再挡一次是省 mux：写向 x0 的指令根本不该往下递值。

前递：两条源，一条 mux

prismexamples/day3/pipe5h.prism · 两个源操作数各自三选一
    // 两个源操作数各自三选一：EX/MEM 递来 / MEM/WB 递来 / 用 ID 读出来的旧值
    wire f_wb : i64 = memwb.q_data
    wire a_fwd : i64 = hz.fwd_a == 1 ? f_ex : (hz.fwd_a == 2 ? f_wb : idex.q_rs1_data)
    wire b_fwd : i64 = hz.fwd_b == 1 ? f_ex : (hz.fwd_b == 2 ? f_wb : idex.q_rs2_data)

拍 4：add（pc=12）在 EX，它的两个源 x1 / x2 分别停在 EX/MEM 与 MEM/WB 里——寄存器堆要再过两拍才更新。可 x3 在拍 7 就是 12：值是从段寄存器门口直接递过去的，没进过寄存器堆。

load 的数为什么不递

第二日那颗 RAM 是组合读，严格说 load 的数在 MEM 这一拍就摆在那儿了，递得出去。但真实 SRAM / cache 是同步读，数要等拍末才落进 MEM/WB——目标机器按"递不到"设计。这一片跟着它走，所以 from_mem_* 上挂了一根 !mem_is_load。代价立刻暴露：下一节那一拍停顿。

停顿：递不了就等

看上面那张表的拍 6：ex_pc 是 20（ld x5,0(x4)），id_pc 是 24（addi x6,x5,1）——后者要的正是前者这一拍拿不到的数。于是 stall 起来。

停一拍的动作是两半：hold_ifid 让 ID 那条原地不动，kill_idex 往 EX 里插一个气泡。表上看得见：拍 7 的 id_pc 还是 24（被 hold 住了），而 ex_pc 也是 24——它等了一拍才真正进 EX。拍 11，x6 出 13。

hold 与 kill 是一对，不能只做一半

把 hold_ifid 单独摘掉（第 8 节的注入 B），后果不是"读到旧值"，而是更糟：那条指令被气泡顶掉了——它进了 EX 却被 kill 清掉 valid，而 IF/ID 已经前进到下一条，没有任何一级会再装载它。x6 永远停在 0。停与冲从来是成对的：一个负责"别丢"，一个负责"别算"。

冲刷：分支在 EX 才定案

这一片没有预测器（那是第五日的事），所以每条分支都要走到 EX 才知道跳不跳——而取指早已往前多走两条。分支的比较借 ALU 做：beq / bne 借 SUB，blt 一族借 SLT / SLTU；funct3 在 ID 就有了，判断在 EX 才用得上，所以它也得跟着段寄存器带下去。

表上拍 9：ex_pc = 32 是那条 beq x6,x6,8，必成立，于是 flush 起来，pcv 从 36 拉到 40。紧跟在分支后面的 addi x9,x0,111（pc=36）在拍 10 进了 ex_pc，可 x9 到拍 11 仍是 0——它带着 valid=0 走完全程。

固定 2 拍惩罚就是这么来的：分支一条，气泡两条。第五日加上 BTB / BHT，才把这 2 拍藏起来。

valid 挡在写回口与访存口

上面那句"它带着 valid=0 走完全程"，其实差一道门就不成立：装配面漏掉下面这一句，x9 会是 111——冲刷看着失效，实情是作废的指令照样落了地。

prismexamples/day3/pipe5h.prism · valid 第一次被用到
    // valid 在这里第一次有人用：kill 清掉的是 valid，可访存与写回的口看的是
    // mem_ren / mem_wen / reg_wen——不拿 valid 挡一下，作废的指令照样落地。
    wire mem_ok : u1 = exmem.q_valid
    wire dm_index : u8 = exmem.q_result[10:3] -> dm.addr
    wire dm_ren_eff : u1 = exmem.q_mem_ren & mem_ok -> dm.ren
    wire dm_wen_eff : u1 = exmem.q_mem_wen & mem_ok -> dm.wen

段寄存器的 kill 只清 valid；可访存口和写回口连的是 mem_ren / mem_wen / reg_wen 这些数据字段。不拿 valid 挡一下，被作废的指令照样把数写进寄存器堆、照样对外设发一次读。

上一集里这个错误不会暴露——那些 kill 恒为 0，valid 也从没被任何地方使用。控制线一活，"作废"才需要真正贯穿到每一个有副作用的口子上。

跑起来：把安全带全拆掉

这一片的程序是第 13 集那个"坏"程序的加强版：依赖全部背靠背，末尾再塞一条必定成立的分支。三条判据同时成立，才算三件事都做对了。

prismexamples/day3/pipe5h.prism · run 块
// 程序：把第 13 集的安全带全部拆掉，再塞一条必定成立的分支进去。
//   0x0c 的 add 紧跟它的两个源   → 靠前递才对
//   0x14 的 ld 紧跟 0x18 的 addi → 前递递不了，靠停一拍
//   0x24 的 addi x9 在分支后面   → 分支成立，它必须被冲掉，x9 得是 0
run pipe5h_check of Pipe5hTop {
    image : {
        prog : im[0:48] = [
            0x00100213,   //  0: addi x4, x0, 1      dm 的字地址
            0x00500093,   //  4: addi x1, x0, 5
            0x00700113,   //  8: addi x2, x0, 7
            0x002081b3,   // 12: add  x3, x1, x2     ← 紧跟，靠前递
            0x00323023,   // 16: sd   x3, 0(x4)      ← 紧跟，靠前递
            0x00023283,   // 20: ld   x5, 0(x4)
            0x00128313,   // 24: addi x6, x5, 1      ← load-use：停一拍
            0x00300393,   // 28: addi x7, x0, 3
            0x00630463,   // 32: beq  x6, x6, 8      必成立：冲掉下面那条
            0x06f00493,   // 36: addi x9, x0, 111    ← 不该执行
            0x00000013,   // 40: nop                 跳到这里
            0x00000013    // 44: nop
        ]
    }
    until : (x6 == 13) & (x3 == 12) & (dm0 == 12) & (x9 == 0)
    show  : { pcv, id_pc, ex_pc, x3, x6, x9, dm0, stall, flush }
}

三发反证：每条判据都得能失败

三件事各自摘掉一处，跑同一个 30 拍窗口（原版在这个窗口里 x3=12、x6=13、x9=0）：

摘掉什么改的那一行30 拍之后
A 前递a_fwd = idex.q_rs1_data
b_fwd = idex.q_rs2_data		x3 = 0　x6 = 1　dm0 = 0
判据从不成立
B 停顿connect 0 -> ifid.holdx6 = 0（指令被气泡顶掉）
判据从不成立
C 冲刷kill_idex = load_use
connect 0 -> ifid.kill		x9 = 111（拍 13 落地）
判据被脏值满足不了
$ prism run .injB.prism --run pipe5h_check --debug （注入 B：只摘 hold）
cycle pcv id_pc ex_pc x3 x6 x9 dm0 stall flush 7 32 28 24 12 0 0 12 0 0 8 36 32 28 12 0 0 12 0 0 9 40 36 32 12 0 0 12 0 1 10 40 40 36 12 0 0 12 0 0 11 44 40 40 12 0 0 12 0 0 12 48 44 40 12 0 0 12 0 0 13 52 48 44 12 0 0 12 0 0

B 这一发最值得看：x6 不是"读到旧值得到 1"，而是根本没有 1——那条 addi 被气泡清掉了 valid，而 IF/ID 没有等它，这条指令不会再出现。少做一半的停顿，比不停更糟。

C 那一发还顺手教了一件事：第一次跑它时判据在拍 11 就成立了（x9 那时还没被写），看着像"没坏"。把窗口拉到 30 拍才看见拍 13 那个 111。判据停得太早，通过是假的。

这一片的边界

没有
多拍单元
这一片没有除法。div / rem 要占住 EX 三十五拍，那属于 M 扩展——第 17 集。届时占用协议还是这套 hold / kill，只是多一个源。
没有
分支预测
每条分支固定吃 2 拍。第五日的 BTB / BHT 才把它藏起来。
没有
跳转与调用
jal / jalr 的写回与重定向没接。程序末尾靠走进 0 指令区停住——Decoder 判非法、控制位全 0，等于一路 nop。
没有
CSR 与陷阱
冲刷这一维在异常上还要再来一次（冲三级）。第 15 集。

小结

  • 三类冒险三种解法：能递的前递（EX/MEM 压 MEM/WB），递不了的停一拍，取早了的冲掉。裁决全在一颗纯组合的 Hazard 里。
  • 段寄存器为什么有 30 个字段：下一段要知道"这条是谁"，不只是"这条拿到什么"。
  • hold 与 kill 是一对：只做一半会让指令被顶掉（注入 B）。
  • valid 必须挡在每个有副作用的口子上——访存与写回看的是 mem_ren / reg_wen，不是 valid。
  • 判据要跑到能看见差异的那一拍：窗口太短的"通过"是假的。
