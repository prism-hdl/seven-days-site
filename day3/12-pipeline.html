        五级流水线
        数据通路

        第 11 集量出来那一拍要串 111 级组合逻辑。这一集不改任何一段逻辑，只做一件事：在它们中间下四刀，每刀放一颗寄存器。下完之后要能跑真程序，跑不过的那一发，就是第 13 集的开场。

        "神说，天下要聚在一处。" —— 《创世记》 1:9
        ← 第 11 集 · 立 flag 第 13 集 · 冒险：停顿、前递、冲刷 →

        流水线没有把逻辑变短

        这是第一次有人把"流水线"当成一种加速手段时最容易搞错的地方：加一级流水，任何一条指令走完全部五段都要五拍，比单周期还慢。它换来的是另一件事——每一拍都有一条新指令进来。

        所以这一集的活很朴素：把第二日那颗核串在一拍里的六段组合逻辑，按顺序切成五堆，堆与堆之间放寄存器。第二日那颗核里，寄存器只有四颗（pc、寄存器堆、两片存储阵列）；这一集要多出四组。

        四组寄存器各收两根控制线。这两根线在这一集全部接 0——先让机器跑起来，再谈什么时候该停、什么时候该冲。这是第 13 集的债。

        五段一张图

        样例在 examples/day3/pipe5.prism。它不重新发明零件——pc、ram、alu、decoder、regfile 五颗全部 import "../day2/…" 第二日的原件，中间插进四颗段寄存器。框上的名字就是 design 里的实例名。

        白虹真核里这四颗更肥：IfId 7 根、IdEx 30 根、ExMem 22 根、MemWb 11 根外加一根 commit。这一片教学核只跑五条指令，字段自然少——但该带什么下去这件事，两边是同一条规矩：下一段要用什么，这一段就带着什么走。

        该带什么下去

        最容易被想错的是 ID/EX 这一颗。寄存器堆是组合读口，读发生在 ID 这一拍，所以往下带的不是 rs1 / rs2 这两个编号，而是已经读出来的值。编号也要带——但那是给 WB 写回用的。

        prismexamples/day3/stage_regs.prism · IdEx 的一拍
            on clock {
        r_pc'       = hold ? r_pc       : d_pc
        r_rs1_data' = hold ? r_rs1_data : d_rs1_data
        r_rs2_data' = hold ? r_rs2_data : d_rs2_data
        r_imm'      = hold ? r_imm      : d_imm
        r_rd'       = hold ? r_rd       : d_rd
        r_funct3'   = hold ? r_funct3   : d_funct3
        r_is_branch' = hold ? r_is_branch : d_is_branch
        r_rs1'      = hold ? r_rs1      : d_rs1
        r_rs2'      = hold ? r_rs2      : d_rs2
        r_alu_op'   = hold ? r_alu_op   : d_alu_op
        r_alu_src'  = hold ? r_alu_src  : d_alu_src
        r_reg_wen'  = hold ? r_reg_wen  : d_reg_wen
        r_mem_ren'  = hold ? r_mem_ren  : d_mem_ren
        r_mem_wen'  = hold ? r_mem_wen  : d_mem_wen
        r_valid'    = hold ? r_valid    : (kill ? 0 : d_valid)
    }

        十五行，每行都是同一个形状：hold ? 保持 : 装载。这就是段寄存器的全部秘密——保持不是"什么都不做"，是"把自己重新写给自己"。写不写由 hold 说了算，而 hold 现在恒为 0。

        其中 r_rs1 / r_rs2 两根编号、r_funct3、r_is_branch 这四行，本集的程序一次都没用到——它们是给下一集那个裁决器预备的：要判"这两条指令撞上了"，光有值不够，还得知道每条指令是谁。

        一拍有三种命运

        四颗段寄存器里，前三颗一样，第四颗不一样。先看不一样的那半句：kill。

        prismexamples/day3/stage_regs.prism · IfId 的一拍
            on clock {
        r_pc'    = hold ? r_pc    : d_pc
        r_instr' = hold ? r_instr : d_instr
        // 数据不 kill：作废的指令也要把位置让给后面那条，只是它自己不算数
        r_valid' = hold ? r_valid : (kill ? 0 : d_valid)
    }

        kill 不是"把这一级清空"，而是数据照常装载、valid 清成 0。为什么？因为被冲掉的那条指令占着的位置要立刻让给后面那条——数据不动反而会把后面那条一起堵死。作废的是身份，不是位置。

        最后一颗 MEM/WB 是唯一的提交点：指令走到这里已经改不了结局，所以它没有 kill，只多出一根 commit。

        prismexamples/day3/stage_regs.prism · MemWb 的一拍
            on clock {
        r_data'    = hold ? r_data    : d_data
        r_rd'      = hold ? r_rd      : d_rd
        r_reg_wen' = hold ? r_reg_wen : d_reg_wen
        r_valid'   = hold ? r_valid   : d_valid
    }

    q_data    = r_data

        这两颗各自跑了一张表，期望是手算的（第 n 拍读到的就是第 n 行输入在拍末落进寄存器之后的值）：

        $ prism run examples/day3/stage_regs.prism --run ifid_check --debug
        cycle q_pc q_instr q_valid 0 17 17 1 1 34 34 1 2 999 153 1 3 999 153 1 4 51 51 0 5 68 68 1 # expect: 6/6 拍有断言 · 3 列 · 全等 ✅

        拍 3 那一行输入换成了 123 / 0x77，输出纹丝不动——hold 生效。拍 4 换成 kill=1，数据 51 / 0x33 照装，但 q_valid 掉成 0。

        $ prism run examples/day3/stage_regs.prism --run memwb_check --debug
        cycle q_data q_valid commit 0 100 1 1 1 200 1 1 2 200 1 0 3 0 0 0 4 0 0 0 # expect: 5/5 拍有断言 · 3 列 · 全等 ✅

        拍 2 值还停在级里（q_data 仍是 200、q_valid 仍是 1），可 commit 掉回 0——停住的那一拍没有指令退休。退休序比对、CSR 的中断采样都要靠这根线，它不能等于"有值"。

        装配面：谁写它，谁就管它

        第三集立过的规矩——边界寄存器由生产方整体拥有——在这里兑现：IF 段写 IfId 的 d 侧，那么它的 hold / kill 也归 IF 这一侧接。装配面上看不到任何"跨段商量"的连线。

        prismexamples/day3/pipe5.prism · IF 段装配
            // ==== IF：pc → im，同拍出指令，然后进 IF/ID ====
    // 这一片没有分支与跳转：pc 的载入端接 0，第 13 集才有人把它换成真信号
    connect 0 -> pcu.load
    connect 0 -> pcu.target

    wire iaddr : u8 = pcu.addr[9:2] -> im.addr
    connect 1     -> im.ren
    connect 0     -> im.wen
    connect 0     -> im.wdata
    connect 0            -> ifid.hold            // 这一集不停：第 13 集才有人拉它
    connect 0            -> ifid.kill
    wire if_pc    : u64 = pcu.addr -> ifid.d_pc
    wire if_instr : u32 = im.rdata -> ifid.d_instr
    connect 1           -> ifid.d_valid

        两个 connect 0 是这一集最诚实的两行：还没有任何东西会停、会冲。第 13 集里它们会换成 hazard 那颗模块的输出，届时全核只有一个人有资格拉它们。

        摆完就跑真程序

        程序很短：算 x3 = 5 + 7，存进 dm[0]，再读回 x7。机器码是 riscv64-elf-gcc 给的，逐条对过反汇编。

        prismexamples/day3/pipe5.prism · run 块
        run pipe5_check of pipe5_top {
    image : {
        prog : im[0:52] = [
            0x00500093,   //  0: addi x1, x0, 5
            0x00700113,   //  4: addi x2, x0, 7
            0x00100213,   //  8: addi x4, x0, 1      dm 的字地址
            0x00000013,   // 12: nop
            0x00000013,   // 16: nop
            0x002081b3,   // 20: add  x3, x1, x2     x3 = 12
            0x00000013,   // 24: nop
            0x00000013,   // 28: nop
            0x00000013,   // 32: nop
            0x00000013,   // 36: nop
            0x00323023,   // 40: sd   x3, 0(x4)      dm[0] = 12
            0x00000013,   // 44: nop
            0x00023383    // 48: ld   x7, 0(x4)      x7 = 12
        ]
    }
    until : (x7 == 12) & (x3 == 12) & (dm0 == 12)
    show  : { pcv, x1, x3, x7, dm0, commit }

        注意那些 nop（0x00000013 = addi x0, x0, 0）：它们不是凑数，是安全带。第 i 条指令在拍 i 取指、拍 i+4 才写回寄存器堆，而第 m 条在拍 m+1 就要读——解出 m ≥ i + 5，就是必须隔开五条。

        $ prism run examples/day3/pipe5.prism --run pipe5_check
        cycle pcv x1 x3 x7 dm0 commit 0 4 0 0 0 0 0 1 8 0 0 0 0 0 2 12 0 0 0 0 0 3 16 0 0 0 0 1 4 20 5 0 0 0 1 5 24 5 0 0 0 1 6 28 5 0 0 0 1 7 32 5 0 0 0 1 8 36 5 0 0 0 1 9 40 5 12 0 0 1 10 44 5 12 0 0 1 11 48 5 12 0 0 1 12 52 5 12 0 0 1 13 56 5 12 0 12 1 14 60 5 12 0 12 1 15 64 5 12 0 12 1 16 68 5 12 12 12 1 # stop: until true at cycle 16

        三条流水线的证据都在这张表上：拍 3 就已经在退休指令（commit 起来时 pcv 才 16），pcv 每拍 +4 一路向前，而 x1 在拍 4 出现、x3 在拍 9 出现——中间隔着的那几拍就是流水的延迟。同一条 run 撞 RTL：

        $ prism cosim examples/day3/pipe5.prism --run pipe5_check
        [run] pipe5_check: RTL tb 跑完，17 拍 [run --cosim] ✅ PASS: pipe5_check golden == RTL 仿真（17 拍 × 6 列全等； golden stop: until true at cycle 16）

        把安全带拿掉：一发注入

        上面那些 nop 看着像装饰。把它们去掉——只改距离、不改任何一条指令的编码——同一颗核立刻给出另一个答案。

        程序指令顺序拍 9 的 x3
        原版addi x1 · addi x2 · addi x4 · nop · nop · add x3,x1,x212
        注入addi x1 · addi x2 · add x3,x1,x2 · addi x4 · nop …0
        $ prism run .inj20.prism --run pipe5_check --debug （注入版，前 16 拍）
        cycle pcv x1 x3 x7 dm0 commit 0 4 0 0 0 0 0 1 8 0 0 0 0 0 2 12 0 0 0 0 0 3 16 0 0 0 0 1 4 20 5 0 0 0 1 5 24 5 0 0 0 1 6 28 5 0 0 0 1 7 32 5 0 0 0 1 8 36 5 0 0 0 1 9 40 5 0 0 0 1 10 44 5 0 0 0 1 11 48 5 0 0 0 1 12 52 5 0 0 0 1 13 56 5 0 0 0 1 14 60 5 0 0 0 1 15 64 5 0 0 0 1 # stop: until true at cycle 16

        x1 在拍 4 就写回了，可 add 在拍 3 就已经把两个源操作数读进 ID/EX——读到的还是复位后的 0。它带下去的是值，不是地址（第 3 节那句话），所以拍 4 的更新追不回来。往后 sd 存 0、ld 读 0，x3 与 x7 一起停在 0。

        这一发不是"设计失误"，是流水线固有的账：段寄存器把指令隔开，也就把它们的读写时刻错开了。第 13 集要做的就是一件半事——把值提前递过去（前递），递不过去的那一类（load 紧跟着用它的指令）停下来等一拍。

        这一片没有什么

        没有
        分支与跳转
        pcu.load 与 pcu.target 接 0。程序跑完就走进 0 指令区，decoder 判非法、控制位全 0，等于一路 nop——机器不停，只是不再做事。
        没有
        冒险处置
        四颗段寄存器的 hold / kill 全接 0，靠程序里的 nop 保持距离。第 13 集补。
        没有
        W 型与移位
        第二日顶层那三样（分支借道 ALU、is_w_op 的符号扩展、移量只取低 6 位）这一片都没搬——它们与"分段"这件事无关，搬进来只会淹没主线。
        没有
        CSR 与陷阱
        非法编码照样被 decoder 举手报出来，但和第九集一样没人接。第 14 集才有人听。

        小结

        • 流水线不缩短任何一段逻辑：它把第 11 集那 111 级切成五堆，最长一堆 34 级；代价是多出四组段寄存器和一套停/冲的规矩。
        • 段寄存器的三种命运：正常装载、hold 整级保持、kill 数据照装而 valid 清 0——作废的是身份，不是位置。
        • MEM/WB 是唯一的提交点：它没有 kill，只有一根 commit；停住的那一拍不算退休。
        • 寄存器堆是组合读口，所以 ID/EX 带下去的是值。这一条决定了下一集：值带早了就是旧的，要么递、要么等。
        • 边界寄存器由生产方整体拥有：谁写 d 侧，谁就也管它的 en / clear。
